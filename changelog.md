# Changelog

## v0.14.0

### Added
- **A material is edited in the game, and the game is what it is edited against** — the parameters of `materials.yaml` were written by hand in a text editor, and the loop of tune-and-look was one of restart the engine, load the map, find the face and read the result back; there was no way to touch a value where its surface stands, which is the only place a brightness or a blend mode can honestly be judged. `qr_light_editor_start` turns the view over to an editor: the player stands where he stood and a free camera takes his eyes, flying with the movement keys and the mouse (the look is always mouse look, `+mlook` or not) and aiming with the crosshair, with `Shift` for a threefold speed and the jump and movedown keys for up and down. A face under the crosshair is picked out by an outline along its edges, and a press of the fire button selects it, leaves the camera where it stopped and opens the material panel docked to the right edge of the screen — the press that selects is swallowed, so selecting never fires the weapon. `qr_light_editor_stop` — the `Exit` button — puts the view back in the player, the weapon and the usual controls with it, and reverts whatever was not applied. The picked texture is looked up through the same normalization the renderer uses, so a face with no material at all still opens the panel, on the defaults, and the material is created on the first change and written out by `Apply` like any other. The material shown for a texture is the group it belongs to rather than a single entry: an animated texture — a medkit, a blinking button — presents every animation frame of its `+Nname` ring as its own section in the panel, each with the full parameter set, so the frames of one object are tuned next to each other and applied together. World faces, brush-entity faces (health boxes, buttons, doors) and liquid and lava faces are all pickable; sky and tool surfaces are not. `Apply` writes every material the engine loaded — and every material the editor created — back to the `materials/*.yaml` file each entry came from, with only the values that differ from the defaults emitted and the header comment preserved; the file a map's own materials came from gets its own entries, and `Cancel` reverts the live materials to the values they were loaded from. The panel owns the mouse while it is open: the camera freezes, the cursor appears, and every parameter is a widget the mouse can drive — a float or an integer (`light_brightness`, `metalness_factor`, `emissive_blend`, `kind`, ...) is a slider with its value written to its right, and the value is also a text field: click the number and type it in. A boolean (`is_light`, `force_rasterize`, `mirror`, ...) is a checkbox, a colour (`light_color`, `color_emissive`) is a swatch with its `RRGGBB` hex value as a text field and an inline editor of three sliders and a hex line, and a texture path (`texture_emissive`, `texture_gloss`, ...) is a text field with a `...` button that opens the file dialog rooted at the game's `textures` directory. A long group of materials scrolls behind a draggable scrollbar with the mouse wheel as its second handle. An edit is applied to the frame on the spot: the changed material is written into the live material tables and re-synthesized (`TexMgr_ReloadImagesForMaterial`), and the traced world — which bakes a material's texture indices when it is uploaded — is asked to re-upload itself (`rt_require_static_submit`, the mechanism the light style cvar already uses), which brings the new textures and the re-collected emissive lights with it. The editor is a mode and not a setting, the two console commands are its only trace in the saved configuration, and nothing it does survives `Exit` that was not `Apply`ed.
- **The `...`-button file dialog** — the texture fields of the material panel open the Windows file dialog rooted in `<gamedir>/textures`, filtered to the image formats the material system reads (`png`, `tga`, `jpg`, `ktx2`), and the chosen file is stored relative to the gamedir with forward slashes, which is the form `materials.yaml` and the texture loader speak.
- **The panel is Dear ImGui** — the widgets the first cut of the editor drew with the engine's own `conchars` — sliders, hex colour fields, texture paths, scrollbars — are Dear ImGui's, vendored under `third_party/imgui` (MIT) with the SDL2 input backend, a dark rounded style and the Roboto font (`third_party/imgui/fonts`, OFL; the build copies it next to the executable, and the built-in font is used when it is missing). There is no ImGui Vulkan backend: the draw lists are converted to `RgVertex` arrays and uploaded through `rgUploadRasterizedGeometry` with the SWAPCHAIN render type — the same path the engine's own 2D draws take — so ImGui brings no pipelines, descriptor pools or frame integration of its own. That needed one addition to the rg API: `RgRasterizedGeometryUploadInfo` carries a `scissor` rectangle now (`RgRect2D`, `width == 0` meaning the whole viewport), and the rasterizer applies it per draw next to the viewport it already applied, because ImGui clips its scrolling regions with scissor rects. Every existing upload keeps its full-viewport scissor. The panel is pinned to the right edge, its material sections are collapsing headers, and the material parameters read as their YAML keys; `kind` and `emissive_blend` are combo boxes, and every slider takes a typed value on Ctrl+click.
- **The panel answers every parameter the same way** — each row carries a square reset button (a circular arrow drawn with the draw list, not a glyph: the panel font has no U+21BA) that returns that one parameter to the value the editor started with — or to the defaults, for a material the editor created itself — and is greyed out while the row still holds it; a texture path that is not authored reads `NONE` instead of an empty field, and typing `NONE` commits as no texture; the numbers of the sliders are limited to two decimals, on screen and in the stored value. The panel takes a quarter of the screen instead of the two-fifths-and-a-tenth it was pinned to, and every parameter explains itself on hover: the hint appears after a second (`ImGuiStyle::HoverDelayNormal`), the fields no renderer code reads say so, and the fields whose meaning depends on the kind of material — `is_light`, `force_rasterize`, `exact_normals`, `light_upoffset`, `light_color` — say that too. The `...` button no longer steps past the right edge: the path field reserves the exact widths of the browse button, the reset button and the item spacings. `mirror` forces `roughness_override` to 0 and locks the slider while it is on, and the synthesis is given the same rule (`mirror: true` with an authored `roughness_override > 0` used to render the override).
- **The world stands still while the editor is open** — the editor is for judging materials, and a medkit that bobs, a button that blinks or a door that moves under the crosshair makes that judging a moving target. The server is paused (`sv.paused`, the flag the game's own pause sets) so monsters, doors, lifts and physics stop, and the client clock is held (`cl.time` no longer advances in `CL_ReadFromServer`) so everything that reads it — texture animations, alias poses, particles, trails — holds as well. Both are restored to the values they had when the editor closes, and only if the editor is what set them. The freeze needs a single-player game: the server pause would stop every client of a listen server, and a remote server cannot be paused from here at all, so the editor refuses to start otherwise.
- **A session is a file, and a mod's materials.yaml is what it becomes** — the editor no longer rewrites each material's source file. `Apply` writes everything the session touched — plus the entries the target already carried, so a copy cannot drop them — to `<gamedir>/materials.editor.yaml`; `Exit` asks "Save all materials changes?" with `Save` and `Discard`: `Save` keeps the previous target as `<gamedir>/backup_materials.yaml` and copies the session file over `<gamedir>/materials.yaml`, `Discard` deletes the session file and puts the values the editor started with back on screen. The target is the running game directory's own file, so in a mod it is the mod's `materials.yaml` (as the requirement puts it, `ad/materials.yaml`), and the loader reads the packaged base first, then id1, then the game directory, replacing entries by name — a mod's materials.yaml overrides the id1 values it names and id1 still supplies everything it does not. The editor's own `materials.editor.yaml` and `backup_materials.yaml` are never loaded as materials, the gamedir's `materials.yaml` also beats a `materials/<map>.yaml` of the same gamedir (it is merged into the map list last), a session file left by a crash or a map change is removed when a session starts, an empty session is no file at all, and a `Save` whose backup or copy fails keeps the session file instead of reporting success.
- **Models and sprites are pickable, and a texture can be sampled for a colour** — the pick only knew the world hull and brush entities, so a medkit (a `b_bh*` model, not a box), an item or a torch could not be selected at all. The trace now also tests the model bounds of every visible alias model and sprite (a rigid transform about the entity's origin; an alias model's bounds already carry its own scale), resolves the skin from the animation frame an alias draws or the sprite frame, outlines the entity's box, and opens that skin's material group in the panel. With `color_emissive` enabled the panel previews the texture the mask is synthesized from — the material's own `texture_base` when it has one, the picked face's engine texture otherwise — and a click on the preview takes the colour of the pixel under the cursor, so the colour a mask is authored against is the colour the synthesis will read. The pixels come from `TexMgr_LoadRgbaForPreview`, which resolves a texture's source the way its reload does. Entities the renderer does not draw (alpha `ENTALPHA_ZERO`) and models without a texture are skipped by the pick, and a sprite is tested and outlined as the camera-facing quad it is drawn as rather than as its bounding box.

### Fixed
- **The picked face is outlined over the finished frame** — the first cut uploaded the outline as world rasterized geometry with a depth test, and it was never visible: the world raster pass draws before the post chain, its fragment stage multiplies the colour by the exposure, and the outline was pushed along `surf->plane->normal`, which points *away* from the viewer on every `SURF_PLANEBACK` face — about half of them — so the depth of the traced surface ate it. The outline now takes the swapchain render type, the overlay path the engine's own 2D and the ImGui panel use: it is projected with the frame's camera matrices, has no depth buffer to lose it to, and is nudged towards the viewer by the sign of the plane normal. Hover is amber, the selected face is white.
- **The panel's mouse cursor moves again** — `IN_Deactivate(true)` frees the cursor but also arms the filter that drops `SDL_MOUSEMOTION`, and the SDL2 backend of ImGui takes the mouse position from exactly those events, so the cursor froze where the panel was opened. A new `IN_FreeCursorForGui` leaves the relative mode off without arming the filter; the events reach ImGui and are consumed by the editor before the engine sees them.
- **The editor owns the interface while it runs** — the engine's HUD (crosshair, status bar, net/turtle/pause overlays, centerprint, dev stats, FPS and RT panels, clock) is not drawn while the editor is active: the hint lines and the centre crosshair are ImGui's now (`QR_GUI_DrawHint`, `QR_GUI_DrawCrosshair`), drawn with the same font and a soft shadow, and only the console stays — it is the way the editor is driven too. The `CANVAS_EDITOR` canvas and `Draw_FillRGBA` that the removed panel drawing had introduced are gone with it.
- **An edit no longer blanks the surface it edits** — the first cut destroyed the material and created a new one on every parameter change, and the traced world (uploaded once per map as static geometry) bakes the material's texture indices: vkpt notifies static geometry with the empty textures when a material is destroyed and never re-notifies when a new one is created, so the first edit turned every surface using that material into a flat, textureless one and nothing could bring the texture back short of a map reload. The flush now asks the world to re-upload itself (`rt_require_static_submit`, the same mechanism the light style cvar uses), so the world picks up the new material handles — and, because `R_DrawWorld` re-collects them on the way, the emissive lights pick up `is_light`, `light_color`, `light_brightness` and the emissive mask of the edit as well. The flush runs before the frame renders (from `V_CalcRefdef`), so the re-upload happens in the same frame the edit was made, and it is throttled while a widget is being dragged so a drag does not rebuild the world every frame.
- **A re-synthesized texture was read back from a garbage file offset** — the BSP loader copies every miptex out of the file buffer into its own allocation (`Mod_LoadTextures`), while the texture task derived the "source offset" it handed to the texture manager from that in-memory copy (`pixels_p - mod_base`, the difference of two unrelated heap addresses). Nothing ever read that offset back: the only live reloader, `vid_restart`, is disabled in this fork. The editor's live re-synthesis is its first consumer, so the first edit of a BSP-embedded texture re-read the map file at the bogus position, converted unrelated bytes through the palette and turned the edited surface into coloured noise — while the same texture had loaded correctly all along, because the initial load passes the pixels directly and never uses the offset. The true offset is computed in `Mod_LoadTextures`, where the miptex pointer still points into the file buffer, kept in `texture_t` and used by the task. The reload also validates the seek and the read range now (naming the offset and the file size, and releasing the file and the buffer when it rejects one), and a glow/luma mask of a different resolution is resampled to its base instead of aborting a Debug build. The reload diagnostics the investigation needed — the per-texture log with the 64-bit offset and the TGA dump of the synthesized textures — are behind `qr_editor_debug` (`0` by default).
- **Cancel and Exit restore the lists completely** — the snapshot restored the material structs but not the list *lengths*, so a material the editor had created for a texture without a yaml entry stayed live with its edited values, kept feeding the panel and the synthesis, and would have been written by the next Apply. The lengths are part of the snapshot now (`RT_MAT_SetListCounts`), and the revert reloads by normalized texture name rather than by material name, so the texture whose editor-created material has just been dropped is re-synthesized as well; the queues that track dirty materials are large enough not to drop names silently. A map change closes the editor before the surfaces it picked and the snapshot it holds are freed.
- **The colour picker opens** — `ColorEdit3` was the one widget that never got an explicit width, so with the 158 px label column before it its swatch was laid out past the right edge of the panel (and of the display); it was unhoverable and the picker could never be opened. It fills the remaining width now, editing a colour enables it (the checkbox stays as the off switch instead of gating the editor), and `color_emissive` says when an authored `texture_emissive` overrides it. The same pass gives every animation frame of a material its own ImGui ID scope (`PushID` per section) — without it the frames of a medkit shared every widget ID, and the picker or a slider of one frame moved the values of the first.
- **The outline of a brush entity is drawn where the entity is** — its vertices are transformed to world space with `RT_GetBrushModelMatrix` (and the picked surface is found in the entity's model space, since a brush entity's planes are local while its trace is in world space); before, a health box, button or door was outlined near the world origin — or not picked at all, because `CL_TraceLine` had reported its internal filtered-array index instead of the entity number.
- **The outline no longer corrupts its own vertices** — it used to take three separate allocations from the engine's scratch allocator, which hands out one shared buffer: the second call zeroed the vertices the first held, the third aliased the vertex array, and a larger face could free the memory being read. One allocation now carries all three arrays.
- **The console works while the panel is open** — the console toggle key passes through to the engine as long as no ImGui text field is editing, the panel stops drawing (and stops taking input) while the console is up, and the free cursor is restored when it closes. The editor's own messages (Apply, Cancel, write errors) are shown in the ImGui notification line instead of only the console log.
- **Apply no longer truncates a materials file** — the writer used to cap a file at 600 materials and the save at 8 files, silently dropping the rest while rewriting the files wholesale. It now writes each source file from whichever list carries its entries (the map copy is synced into the global list first, file names are matched case-insensitively), with no per-file cap, and a failure is reported rather than written. Only the files that hold an edited material are rewritten — a file nobody touched keeps its comments, formatting and keys the loader ignores — and each one that is rewritten gets a `.bak` copy first.
- **`light_brightness` is a gain on the emitted light again, and it goes to 5** — the value was folded into the 8-bit emission channel of the RME texture and clamped there, so past the saturation point every value drew the same maximum-bright surface, and below it the surface darkened while the light itself was scaled through an RGB→HSV→RGB round trip that cannot brighten a colour (its V is clamped at 1) and divided by zero at `light_brightness 0`. The visible emission is dimmed by `min(brightness, 1)` — an 8-bit channel cannot brighten — and the emitted light takes the full float gain exactly once: an area light whose mask the shader samples is already dimmed by that mask below 1, so the gain stays out of it there, above 1 the gain on the light colour is what brightens, and a material whose light comes from `light_color` alone is no longer skipped by a mask-shaped gate. The glow extents of a mask are its shape and no longer move with the brightness, and the slider spans `0..5`. A `light_color` or `is_light` switched off mid-session stops lighting at the next re-synthesis rather than at the next map load, the `...` button no longer steps past the right edge of the panel, and the panel is a quarter of the screen wide instead of the two-fifths-and-a-tenth it was pinned to, with a 352-pixel floor below which its fixed columns stop fitting.
- **The material keys no renderer code ever read are gone** — `kind`, `texture_mask`, `specular_factor`, `bsp_radiance` and `default_radiance` were parsed, offered by the editor, written back by `Apply` and read by nothing: `kind` advertised water, lava and glass behaviours this renderer does not switch on, `texture_mask` was a texture path no load ever asked for, `specular_factor` fed no BRDF (the shader's dielectric F0 is its own), and `bsp_radiance` and `default_radiance` named a radiosity pass the engine does not have. The fields, their parser branches, the `kind` name table, the panel rows and the writer's emission of them are removed together, so a save can no longer add a key that does nothing; no shipped material file authored any of them, and a foreign one that does loads with the parser's usual `unknown attribute` note.

## v0.13.0

### Added
- **The weapon can be held smaller and closer than the room it takes up** — `rt_viewm_scale` (`0.32`) draws the weapon of the fist `0.32` times smaller and, by that same factor, carries its zero that much closer to the eye, which is what keeps it the weapon the player knows: the picture of it in the frame is untouched, and it is the room it takes up in the world that shrinks with the factor, under a third of it at `0.32`. What that comes to is a weapon that is out of the walls: the barrels of `id1` reach from `19` to `54` units forward of the eye (`v_shot2` to `v_rock2`), so `6` to `18` of them, where the player's own hull keeps that eye `16` units off a flat wall, and no barrel of the fist is drawn through the wall in front of it any more. The axe is the one weapon left out of that — its head being swung over most of `75` units of the room the player stands in, `25` of them at `0.32` — and `0.1` is where even that comes under `8` units of the eye, which is a wall out of reach of anything the fist holds. The near clip distance is where the scaling stops being invisible, and it is `GL_GetCameraNear` that carries it: the ray-traced frame starts its primary rays and cuts its projection at `4` units from the camera (less at a wider field of view, and `0.5` of a unit at the floor of the reading), so a weapon drawn `0.32` times closer than that distance stands inside the near plane and is clipped away — the distance is taken from the same factor, `4` units going to `1.28` and the floor of them to `0.16`, which is where the weapon of a scaled frame comes back. What that brings with it is the near plane of the whole scene and not of the weapon alone, since the traced frame carries one near distance: the primary rays of a scaled frame start `1.28` units from the camera instead of `4`, its projection, its FSR2 setup and its volumetric pass are read off the same number, and the geometry the near plane used to cut away around the player — the floor at his feet, the wall at his shoulder — is traced with the weapon. The factor is archived, `1` is the weapon as it always was, and the setting composes with `rt_viewm_fovscale` and `rt_viewm_wide`, which shape a weapon across the view where this one shapes it away from the player.
- **The sky is the colour it is set to, and the clouds are a colour of their own** — `rt_sky_color` never reached the picture as the colour it names, twice over: the host multiplied it into the value it sent (`RT_APPLY_SKY_COLOR`, whose single caller it was) and `CmProceduralSky.comp` then used that same value as the *strength of a tint*, mixed by an amount taken from its own luminance and saturation — so the shipped `32 0 64` was applied to itself and arrived darker than it reads — while what the mix was applied *to* was not the sky the setting names at all but the analytic single-scattering atmosphere the file was ported with, Rayleigh and Mie over a planet radius with a solar irradiance and a radiance scale. The atmosphere is what a sky set to any colour used to be mostly made of: a black `rt_sky_color 0 0 0` drew the raw physical blue (the amount of tint collapsed because black is neither bright nor chromatic, which is what v0.12.4's `max(tintChroma, 1 - tintLum)` was for), and every other colour arrived as that colour mixed with a bright blue sky. The atmosphere is gone — its constants and its functions (`PLANET_RADIUS`, `BETA_RAYLEIGH`, `BETA_MIE`, `raySphere()`, both phase functions, `SOLAR_IRRADIANCE`, `RADIANCE_SCALE`) are deleted — and `evaluateSky()` now returns the colour it is given: the procedural sky is a flat colour and the clouds over it, nothing else. `rt_sky_tint` goes with it, being the strength of the tint that no longer exists, and the slot it occupied (`RgDrawFrameSkyParams::skyColorSaturation`) carries the opacity of the clouds instead, `rt_sky_cloud_alpha` (`1.0`): the clouds are composited over the sky in the colour of `rt_sky_clouds_color` at that opacity, clamped, so they can be *darker* than the sky they hang in — the default `0 0 0` is exactly that, black cloud over a coloured sky — and `0` takes them out of the sky entirely. Their contour is what `rt_sky_cloud_density` (`0.8`) shapes now, in place of the thickness it used to stand for: the band its noise is faded over across the coverage is `mix(0.7, 0.05, density)`, so the cloud is a hard-edged silhouette at `1` and a soft one at `0`; coverage, drift speed and the `rt_sky_clouds` switch are unchanged, and a cubemap of clouds that are switched off or fully transparent is still cached (the cloud time is frozen with it, because a cloud that animates under `rt_sky_cloud_alpha 0` would re-render the cubemap every frame for a picture that cannot change). The sun's disc is what remains of the sky's own light: it is drawn on top of the flat colour in `rt_sun_color` and kept out of the ambient cubemap exactly as before, and the physical angular radius of the sun stays ignored, as it has been — the disc's size is the display radius in radians (about a degree and a half), because the real one is a fraction of a pixel. `rt_brightness`, `rt_sky` and `rt_sky_brightness` still scale the sky once: the host no longer pre-scales the colour it uploads for the procedural sky (the shader multiplies the whole sky, disc included, by the sky multiplier) and the indirect light of the sky no longer multiplies the multiplier a second time — the cubemaps the compute pass fills carry it already, so `getSkyFilteredMultiplied()` now returns the procedural sky as it is, where a `rt_brightness` of `0.75`, say, used to light surfaces from the sky at `0.56` of it while the sky itself was drawn at `0.75`. A classic sky *texture* is untouched: there `rt_sky_color` is the tint over the texture, as it always was, and the texture is what the two multiply. The default picture therefore moves: the sky of `id1` is the violet it is set to rather than that violet mixed with a blue atmosphere, and the ambient light it casts is the colour of the sky rather than the colour of a planet's sky. No field of the public `RgDrawFrameSkyParams` was added or moved — the cloud settings still ride in the rotation matrix the procedural sky leaves unused, and the new cvar in the tint slot — so the change stays inside the shader and the host.

## v0.12.4

### Fixed
- **An emissive texture lights the animation frame it shows** — a textured area light was pinned to a single frame of its texture's animation, so a lamp whose cycle contains an unlit frame lit the room from its lit frame whatever it drew. The pinning itself is deliberate and stays: `RT_CanonicalLightTex` picks the first frame of the `anim_next` ring that lights at all, because the visible pass switches every animated texture of a map on one timer (`R_TextureAnimation` reads `cl.time * 10`), and a frame that depends on that timer would move the light's identity and the cluster lists that name it from frame to frame — the flicker of the whole scene the canonical choice exists to prevent. What was wrong is that the one place meant to follow the animation asked for frame `0` (`RT_AnimatedLightTex`), which is the frame the canonical choice returns, so the per-frame update of a stored light was a no-op for every surface of the world. A blink — `+0basebtn` lit between a red lamp and a dark one, `+1basebtn` with `is_light: false` — therefore kept its light, and a teleport or a button that steps to another emissive frame stepped its emission nowhere. An entity light is not stored between frames, so `RT_AddEmissiveLight` now reads the frame where the surface is: `rt_uploadsurf_state_t.diffuse_tex` is filled from `R_TextureAnimation` by both drawing paths, i.e. it is the frame the visible pass renders — the entity's own frame and the alternate ring included — and the light takes the emission of that frame, its material, its mean brightness and its colour when the frame lights by itself, and no emission at all when it does not, with deliberately no fallback to the frame the light was picked from: the base is the lit frame of a blink, so reading it back is precisely the lamp that never goes out. Identity, geometry and the glow extents stay with the canonical frame, so no light moves in the light array or in the cluster lists, and the shape of a light does not change with the frame either — whether a face is cut into pieces of itself or replaced by the square that carries no mask is a property of the mask, not of the frame that is burning. A dark frame dims its light through `RT_KeepEmissiveLightColor` instead of dropping it: the light manager keeps a light by its colour, and a light removed and added again leaves a hole in every cluster list naming it, which is the flicker the canonical frame exists to prevent. Nothing changes for the world's own stored lights, and the two halves of the story explain the report: a lamp that belongs to the world already followed its animation, because `RT_UploadAllWorldModelLights` re-derives the emission of every stored light from the frame its surface shows on every frame and dims a light rather than dropping it — while a button, a door and a moving platform are brush entities, and their lights are not stored anywhere between frames, so they were the ones that never went out. A frame the renderer has not resolved is left out of the reading, so a light keeps the emission it would have had without this change.
- **The LF deflicker of the ASVGF denoiser is back, with the neighbours it needed** — the low-frequency pass that cuts an isolated spike in the temporal result before the a-trous iterations smear it over its surroundings was disabled in v0.12.3, where it darkened the light around dark silhouettes, and its own note recorded what had to change before it could return. All three points are addressed and the pass runs on iteration `0`, as it does in Q2RTX. Its neighbours are now validated the way `filter_image` validates its own — a relative depth difference under `Q2_FLT_DEFLICKER_DEPTH` (`0.1`) and a geometric normal within `Q2_FLT_DEFLICKER_NORMAL` (`0.5`) of the pixel's — so geometry that merely sits next to a pixel (the weapon in a bright room, the frame the screen is drawn in) cannot drag its light down. `Q2_FLT_ATROUS_DEFLICKER_LF` went from `0.75` to `2.0`, the value Q2RTX ships as `flt_atrous_deflicker_lf`: it is a ratio against the mean of the neighbours, so anything below `1` darkened flat, evenly lit regions to a fraction of their light. The fetches are bounded to the checkerboard field the invocation owns and an out-of-range tap is skipped before it is fetched, since an out-of-range `texelFetch` is undefined; the mean is taken over the neighbours that passed validation, so there is no division by zero, and a pixel with no valid neighbour — or one that carries no light at all — keeps its own sample untouched. The fireflies it was re-enabled for turned out to come from the sun's share of an indirect bounce (`rt_sun_bounce_scale` and `rt_sun_bounce_range`), not from the low-frequency channel, so this restores the pass because it is correct and not because it was the cure.

## v0.12.3

### Fixed
- **The `{`-fence textures cut their shapes out again** — a texture whose name begins with `{` carries an alpha channel of its own, and only the rasterized path ever tested it: the world marks such a surface `SURF_DRAWFENCE` and the raster shader discards a texel under `0.5`, while a *traced* surface is uploaded as a pass-through type and the world passed every brush as `RG_GEOMETRY_PASS_THROUGH_TYPE_OPAQUE`. Rasterization is not the fallback it looks like — `RT_FlushBatch` sends only translucent geometry to the rasterizer, and a fence belongs to the opaque world (entity alpha `1`) — so the openings, vines, webs, ladders and grates of the maps were traced with their alpha ignored and drew as solid rectangles whose transparent texels went black. Fence surfaces now take `RG_GEOMETRY_PASS_THROUGH_TYPE_ALPHA_TESTED`, whose hit group runs `RtAlphaTest.rahit`, the any-hit shader that already cut out traced sprites. The order the world picks its types in is unchanged, so a mirror, water, acid and a teleport portal keep their own. An alias model with `MF_HOLEY` — the flag that makes colour index 255 of a skin transparent — takes the same type, since models were traced opaque as well and the two models in the game data that carry the flag are almost entirely transparent and drew as solid plates. Nothing else about the model path, the rasterized alpha test (still what a translucent entity gets) or the alpha test itself moved: a fully transparent texel is discarded by `RtAlphaTest.rahit` whatever its colour is.
- **The LF denoiser no longer darkens the light around a dark silhouette** — the low-frequency pass of ASVGF filtered with a deflicker that clamped every pixel to `Q2_FLT_ATROUS_DEFLICKER_LF` (`0.75`) times the mean of its eight neighbours, and that constant is a ratio against the mean rather than a floor under the pixel: below one it darkened flat, evenly lit regions to three quarters of their light, and it left a black halo around whatever dark geometry stood in front of a lit wall — the weapon in a bright room, the frame the screen is drawn in. Its neighbours were taken without the depth and geometry-normal tests that `filter_image` validates with, so geometry that merely happened to sit next to the pixel (a different surface) pulled its light down. The pass no longer runs: the first iteration of `CmQ2AtrousLF.comp` now copies the low-frequency image into the ping-pong target instead of deflickering it. The pass itself stays in the file behind a note of what has to change before it can return — validate its neighbours by depth and geometry normal the way `filter_image` does, keep the constant at or above `1` (Q2RTX ships `flt_atrous_deflicker_lf = 2.0`), and bound its fetches.
- **The LF denoiser and the upsample no longer read texels they have not checked, and no longer take one invalid texel for the whole pixel** — an out-of-range `texelFetch` is undefined, and the zero weight that was meant to discard such a texel does not discard it: `NaN * 0` is `NaN`, so an invalid texel survived the accumulation and spread over the pixel. Three reads were at fault. The neighbour test of `filter_image` (`CmQ2AtrousLF.comp`) fetched the texel it was comparing, and the comparison only became a weight; a neighbour outside the field is now skipped before the fetch and the weight is `1.0`. The tap test of `interpolate_lf` (`CmQ2Atrous.comp`) fed the same comparison into a weight, so an invalid tap arrived in the sum with a positive weight whenever the edge fallback fired. And the LF pass admitted an invocation whose own anchor texel lies outside the image whenever the render size is `3k + 1`: the guard tested `ipos * Q2_GRAD_DWN`, while the texel it reads is `ipos * Q2_GRAD_DWN + ivec2(1)`. The neighbour loop of the temporal pass rejected a row above the image but not a row below it (`CmQ2Temporal.comp`, now `p.y < 0` as well). Every result that was inside the image is unchanged: the weight was only ever multiplied by factors at or below one, and the case these guards drop — a tangent frame facing away — already carried a weight of zero.
- **A rasterized particle batch is uploaded with its own vertex count** — `PScript_DrawParticleTypes` (`r_part_fte.c`) sent every particle batch of a frame to the rasterizer with a hard-coded `.vertexCount = 4`, on the assumption its own comment recorded — that the `x` of the buffer test `cl_numstrisvert + 'x' > cl_maxstrisvert[]` never exceeds four. A particle type whose polygon carries a different number of vertices was therefore drawn from a count that was not its own, which is what broke the particles of Arcane Dimensions and of the 2021 remaster. The count is the batch's own `tris->numvert` now.

## v0.12.0

### Added
- **The sun has a colour of its own** — the sun took its colour from the sky (`rt_sky_color`), so a sky tinted dark violet — the shipped `32 0 64` — also made the only natural light source violet, and darkening the sky for a night or an alien look dimmed the sunlight with it: there was no setting that reached the light without repainting the sky, because the two were one value. `rt_sun_color <r 0..255> <g 0..255> <b>` is the fifth row of the colour table in `gl_vidsdl.c` — a command over an archived cvar exactly like `rt_sky_color`, so `rt_sun_color "255 255 255"`, `255,255,255` and a bare `rt_sun_color` behave the way the other colour settings do — and everything that *is* the sun reads it: the directional light the host uploads (`gl_rmain.c`, and with it the indirect sun of `rt_sun_bounce_*`, the god rays, whose inscatter is that colour, and the sun's shadow map), the sunlit shafts of the fog (`RgDrawFrameVolumetricParams.sourceColor`, scaled by `rt_volume_lintensity`) and the sun proxy a rasterized sky hands the god rays (`Sky_GetBrightestPoint`). The drawn sky keeps `rt_sky_color`, and the disc of the sun inside the procedural cubemap is painted with the sun's colour as well, not with the sky's: the atmosphere around the sun is tinted and the sun itself is not, so the two settings no longer have to agree and a sky taken out with `rt_sky_color 0 0 0` keeps its sun. That disc used to be the sky tint scaled by a hard-coded `750`; the shader's sky-tint field is now named for what it is (`skyTint` in `ProceduralSkyParams` and `CmProceduralSky.comp`), a `sunDiscColor` field beside it carries this setting into the compute pass, and the intensity constant is rescaled because it now supplies the whole brightness of the disc: `6` is the tint it used to be multiplied into (`0.0079` luminance times `750`; the tint reaches the shader twice, once as the colour and once through `RT_APPLY_SKY_COLOR`), so the disc is as bright as it was at the shipped `32 0 64` — and now equally bright at every other tint, where a white sky used to carry a disc some hundred times brighter than a violet one. The disc reaches only the visible sky cubemap and never the disc-less `envCubemap` the indirect sky samples, so no light level moves with it, indirect or otherwise. `RT_SunPreset_f` writes `rt_sun_color`: the presets are sun colours — they wrote `rt_sky_light_*` before the two settings were merged into one — and repainting the sky was their side effect rather than their point. The default is white, which is a change to the default picture: the code channel of the sun went from the sky's `0.25` and its red from `0.125` (green from `0`) to `1` across, so `rt_sun 1` now delivers about twenty times the daylight of 0.10.0 in luminance, in white instead of violet. Nothing else about the sun moved — the fraction `RT_SUN_LIGHT_INTENSITY_SCALE` and the fixup are untouched — so a scene tuned against the old daylight wants `rt_sun` around `0.05`, or a new `rt_sun_color`, rather than a new calibration of the sun.
- **The sun can be placed by aiming at it** — aiming the sun meant typing two numbers into the console and looking at the result: one `rt_sun_pitch` / `rt_sun_yaw` guess per attempt, and no way to point at a particular gap in the geometry. `rt_sun_edit 1` makes the sun an editor — while it is on, the two settings are written every frame to where the crosshair points, which is the centre of the screen and therefore the view vector of the frame with the bob and the weapon kick included, and a press of the fire button leaves the sun there and takes the mode off. The press that ends it is swallowed rather than passed on, so leaving the editor does not also shoot the weapon it was aimed with. Only those two cvars are written, and nothing about the sun is special: the directional light the host uploads and its shadow map, the indirect sun of `rt_sun_bounce_*`, the god rays, the fog's sunlit shafts and the disc the procedural sky draws all read them, so the sun moves on screen the moment it is aimed. The pitch is mirrored and the yaw turned around, because the uploaded direction is the direction the light *travels* in — away from the sun as seen from the eye — and the sun follows the crosshair only when the two are opposite. The editor is a mode and not a setting, so it carries no `CVAR_ARCHIVE` flag: a saved configuration would otherwise end every later session with a sun that follows the crosshair without anybody asking for it. The cvar is registered with a callback rather than compared by string: turning it on says what to do and warns when `rt_sun` is `0`, where there is a sun to place but none to see, and turning it off prints the pitch and the yaw the sun was left at. A cvar whose value has not changed is not written, so a still camera costs nothing per frame.
- **`cfg_write` and `cfg_exec`** — a configuration could only ever be saved as `config.cfg`, so a second one (a test setup, a machine's own bindings) had to be kept by renaming files by hand. `cfg_write <name>` writes the key bindings and the archived cvars to `<name>.cfg` in the current gamedir, and `cfg_exec <name>` runs such a file back. Like `config.cfg`, the file ends with `vid_restart` and, when mouse look is on, `+mlook` — that trailing `vid_restart` is what made a replayed configuration disturb the renderer's textures (see the `vid_restart` entry below).
- **A material can choose its own emissive blend mode** — how an emissive surface is composited was set by the global `rt_emis_blend` cvar alone, so a material that needs a different mix had no way to ask for one — a glowing mirror, for instance, where the default blend washes the reflection out. A material may now author `emissive_blend` in `materials.yaml`, and its value is used for that material's emission with the cvar as the fallback for everything that does not carry one. The authored mode travels with the emission rather than being looked up again at the end: the texture manager packs it into the alpha of the roughness/metallic/emission texture as `mode + 1` (`0` meaning "follow the cvar"), the primary and reflection rays pick it up there and carry it in the alpha of `framebufPrimaryToReflRefr`, and the compose pass resolves it per pixel. Rasterized emissive surfaces write the same value, so both paths agree on what a surface is.
- **A classic sky casts its shafts from its brightest point** — the volumetric shafts need a direction to scatter sunlight from, and the procedural sky has one, but a classic Quake sky texture (and the Quake 64 sky boxes) carries no directional light at all: with `rt_sun 0` there was nothing to scatter and `rt_godrays 1` drew no shafts over such a sky. `Sky_GetBrightestPoint` resolves the brightest spot of the sky the renderer is currently drawing — its texture coordinate, its direction, its colour — the rasterized sky pass reports it through `RgDrawFrameSkyParams`, and the device uses that direction for both the shadow map and the inscattering phase function while the physical sky is off.
- **A release bundle script** — `bundle_release.ps1` packages a Release build into `dist/QuakeRay-<version>-win64.zip`: `quakeray.exe`, the runtime DLLs, and the `id1` runtime assets (`materials`, `mdl_skins`, `progs`, `shaders`, `textures`, and the `BlueNoise_LDR_RGBA_128.ktx2` / `WaterNormal_n.ktx2` files) together with `readme.md`, `changelog.md` and `LICENSE.txt`. The version in the archive name is read from `ENGINE_VERSION` / `ENGINE_VER_PATCH` unless `-Version` passes one in, debug artifacts are never included, and the original game data is not bundled — the user supplies `PAK0.PAK` / `PAK1.PAK` from their own copy of Quake.

### Fixed
- **A black `rt_sky_color` painted the brightest sky of all** — taking the sky out (`rt_sky_color 0 0 0`, a night, a test frame) produced the raw physical atmosphere, bright blue by construction, instead of black. The tint of the procedural sky (`CmProceduralSky.comp`) was applied by saturation, `tintAmount = clamp(tintStrength * tintSat / (tintLum + 1e-5), 0, 1)`, and black has neither luminance nor saturation, so the amount collapsed to zero and the `mix()` behind it returned `inScatter` — the untinted Rayleigh and Mie sky. The amount now takes the darker of the two properties as well, `max(tintChroma, 1 - tintLum)`, so a tint counts when it is coloured *or* dark, and the `0 0 0` case reaches the `mix()` at full strength. Every other tint keeps the amount it had: a tint that carries chroma against its luminance is already clamped to `1` at the shipped `32 0 64` (chroma ~5 against a darkness of ~0.96) and stays there, and only a tint near black — the only place the two terms disagree — moves.
- **The shafts no longer leak through walls, and they reach what they fall on** — the shadow map the shaft march reads was drawn with every face kept (`VK_CULL_MODE_NONE`, because the Q1 geometry upload has no winding the rasterizer can be trusted with), and the march biased its samples along `-sunDirection * 20` (Q2RTX's own value), which thickens occluders. With the near side of a surface in the depth buffer, that bias pushed the last samples of a ray *behind* the surface and the end of the shaft read as shadowed — the dark gap between a shaft and the floor or wall it fell on. Biasing the sample back toward the sun (a `+1` offset) closed the gap but let the light through thin walls and at grazing angles. The pass now matches Q2RTX exactly: front faces are culled, so back-face depth is what the shadow map stores, and the march keeps the `-20` offset and never samples the final step before a surface. A sample pushed behind an occluder now compares against its far side and still reads as lit, so a wall occludes without cutting the shaft short of it. Q1 BSP surfaces are wound consistently (counter-clockwise from the front), so the cull mode Q2RTX uses for its own geometry works here unchanged.
- **Emissive textures stopped glowing behind water and acid** — the extinction of a participating medium is derived as `-log(mediumColor)` in `getMediaTransmittance` (`Media.h`), and a channel that is exactly zero — the red channel of the acid colour is — makes that logarithm infinite. The zero extinction was then multiplied by the distance as `0 * inf`, so everything seen through water or acid came out as NaN and the emissive textures behind it went black (the water and the acid share this medium code, which is why both were affected). The argument of the logarithm is now clamped in both branches (`max(colour, 1e-6)`), which is the whole of the change.
- **The world cluster tables are built around the solid leaf** — the tables were built as if leaf 0 were a leaf like any other: it was given a PVS row of its own, its own bounding box, and a cluster index, while the surfaces of the solid brushes needed a cluster to fall into. Anything mapped to leaf 0 therefore landed nowhere, and a leaf at the very edge of the table could be rejected. Cluster 0 is now reserved for the solid leaf and for geometry with no leaf of its own — it covers the whole model, carries the solid flag and no PVS row — and a surface's cluster comes from the leaf its centre resolves into (`RT_SurfaceCentroidLeaf`), which is also what a cached world surface resolves to instead of the last leaf whose marksurfaces list happened to name it. The leaf-to-cluster mapping, the vis-row projection and the sky visibility walk all follow.
- **The shadow map follows a moved entity** — the shadow map pass projected brush vertices with the view-projection matrix alone, so the shadow of a moved entity stayed where its brush was originally placed while its geometry moved. The world position that the shadow map vertex shader reads comes from the traced vertex buffer, which is not transformed for dynamic geometry, so the model matrix now travels in the push constant and is applied in the shader. `VertexCollector` recovers that matrix per draw by mapping the transform's device address back to an index in the transforms buffer the traced path uses, so the shadow map and the RT path agree on where the geometry is.
- **A textured area light samples the mask its surface shows** — an emissive texture that carries a mask (a lamp face, a window, a rune) glowed as if the whole polygon emitted: the visible surface read the emission mask out of the roughness/metallic/emission texture and the area light never did, so a lamp bright in its centre and dark around it lit the scene from its whole face. The host wrote the material of the light as `RG_BLEND_FACTOR_ONE` (`RT_EmissiveLightParamsForTex`), which is the first `RgBlendFactor` and therefore zero — exactly `RG_NO_MATERIAL`, the value the renderer reads as "no mask, the whole texture glows, at the brightness of the light". The parameter is now the surface's own light material whenever it has one, and a mask is decided by the texture alone rather than by its average brightness: a mask that is entirely black is a light of no emission, not a light of the whole texture. `sampleTexturedAreaLight` (`Light.h`) reads the mask in the point it samples and applies it exactly once, so a point the mask leaves black contributes nothing and casts no shadow ray; the light keeps the geometry of its surface as well — a masked face with more corners than a light polygon carries is cut into convex pieces along the surface's own corners, up to sixty-eight of them, each uploaded as a light of its own with its own identity, area and corners (`RT_SplitUvPolygon` in `r_world.c`), and a face past that keeps the square that stands in for it, which glows evenly at the mean of the mask instead of reading the mask through a uv the surface does not have. The average brightness is no longer the mass a light is picked by — a textured area light is placed by its solid angle, as the selection entry below has it — and it now describes the emission of a light whose texture has no mask, which is the one case where a single brightness speaks for the whole polygon. A light style stays a scale on the colour, each applied once, and the material now follows an animated frame the way the colour and the brightness already did.

### Changed
- **The emissive materials are retuned and re-masked** — `light_brightness` came down almost everywhere: the emissive textures were lighting the maps far too strongly, and the RT brightness is now set from the game's own light levels rather than from the raw masks. The window, wizard-window, rune, key/card and lamp materials take their emission from `*_luma` masks authored for them instead of from the base texture or a shared mask, the medkit variants (`+1_med25`, `+1_med25s`, `+2_med25`, `+3_med25`) have entries of their own, and the rune, key and card materials carry their light colour. The window and wizard-window base images that only duplicated the game's own art are dropped, so those materials name the game texture through `texture_base` and contribute only the emissive mask, and the obsolete fullbright masks that were renamed are replaced by the new ones. A second pass took the remaining lamps up (`tlight03/04/05/06` from `0.05` to `0.2`, `ceil1_1` from `0.03` to `0.2`, `tlight07` to `0.1`), brought `switch_1` down to `0.05` and `z_exit`/`comp1_6` up to `0.05`, gave `tlight03` the luma mask it was missing, added `tech06_2` as a red light with a mask of its own, and listed `tlight01_2` as the non-light variant of `tlight01`.
- **The textured area lights follow Q2RTX** — lighting from emissive textures diverged from Q2RTX in three ways and looked wrong next to it. *Sampling* (`Light.h`): a polygon is now sampled on its own surface with no normal offset and attenuated by a `sqrt` spot factor around its normal, as Q2RTX's `sample_polygonal_lights` does, instead of culling coplanar surfaces and offsetting the sample off the plane — surfaces next to the light are lit the way the game lights them. *Selection* (`Q2LightLists.h`): the bruteforce sampling budget grows from 8 to 16 lights, and a textured area light is no longer weighted by its mean emission when it is picked; its solid angle is what places it. *Noise* (`CmQ2Adapter.comp`): the firefly filter starts its neighbour luminance at `1.0`, so a pixel with no valid neighbour is not mistaken for a firefly. *Style and animation* (`r_world.c`): the light keeps its identity and its geometry and re-derives its emission from the animation frame the surface shows and from its light style; a light that is switched off is dimmed in colour instead of having its selection mass zeroed or its colour dropped below the light manager's threshold, because an id missing from a frame's light array leaves a hole in every cluster list that names it — the whole-scene flicker. `rt_truelight 0` is now able to switch the emissive-texture lights off entirely.
- **`vid_restart` is a stub, and the material reload it carries is out of reach** — editing `materials.yaml` no longer needs a full engine restart: `vid_restart` re-reads the file (and the per-map override list) and re-applies the material properties to every image texture, and the map the materials were last loaded for is remembered so the per-map overrides are rebuilt as well. A glow/luma image is loaded as a second pass over its base texture and carries that base material's emission mask, which is derived while both images are loaded, so `TexMgr_ReloadAllImages` had to be taught to replay the pair: the sidecar now keeps its own file as its source file and the special pass no longer asserts when the albedo image cannot be read back, or a reload dropped the mask and the textures stopped glowing. Re-initializing the renderer in place does not rebuild the material and image caches consistently, though, so `vid_restart` currently prints a notice and does nothing, and the body it used to run sits behind `#if 0` until those caches can be re-initialized correctly. `vid_restart` is also the last line of every saved configuration, so a configuration replayed through `exec` is what used to break the textures.
- **`gr_intensity` is now `rt_godrays_intensity`** — the engine's ray tracing settings carry the `rt_` prefix, and the strength of the sun shafts kept Q2RTX's own name for the cvar. The value and its meaning are unchanged (`1` is the shipped strength, `2` doubles the shafts, `0` takes them out), but a configuration that sets `gr_intensity` needs the new name.
- **The engine reports itself as QuakeRay** — `version` printed the Quake and QuakeSpasm versions the engine derives from, and the QuakeC engine string the CSQC init extension receives was `vkQuake`. Both now say QuakeRay.
- **The README is a short overview again** — the long feature dump inherited from vkQuake is replaced by an overview, a Features/Graphics list and a Roadmap.

### Removed
- **The vintage render-scale mode** — the `320x200` / `640x480` / CRT / `1024x768` internal resolutions and the sharpening they forced are gone, together with the Vintage row of the video menu and the `rt_vintage` cvar. `rt_renderscale` keeps the render scale and `rt_ef_crt` keeps the CRT screen effect.

## v0.10.0

### Added
- **Classic level fog in the ray-traced renderer** — the map's `fog` key and the `fog <density> <r> <g> <b>` console command (how Arcane Dimensions' `globalfog.qc` changes the fog at runtime, 46 of its 284 maps carry the worldspawn key) now tint the frame instead of doing nothing. The falloff is the original one — `f = exp(-(density * distance)²)`, `mix(fogColor, color, f)`, with the density scaled by `1/64` as `Fog_SetupFrame` scaled it and the distance being the fog coordinate the classic renderer used, the perpendicular view depth. The blend runs in `CmPrepareFinal.comp` after the rasterized geometry and after the classic acid fog, so sprites, `rtforcerasterize` models and the viewmodel are covered together with the world, and it never touches the bloom buffer. Because the frame buffer stores the ray length rather than the view depth, the ray is corrected by its own view-forward cosine, which keeps the fog from thickening toward the edges of the screen. The sky keeps the classic `skyfog` blend (`sky * (1 - skyfog) + fogColor * skyfog`) rather than the exponential, and `rt_level_fog 0` turns the level's fog off without discarding it.
- **One command for the on-screen statistics, and a dump to file** — the readout used to be three separate commands, each drawn in its own font at its own size, so on a 4K screen they were three blocks that could not be read as one picture. They are now one command, `rt_stats 1,2,3`, where the argument lists the panels to show: `1` the ray counters, `2` the GPU pass timings, `3` the CPU frame profile. The panels stack in a single block at the size the GPU panel already used, the frame rate gets its own line at the top and every section starts after a blank line, so the numbers line up in two columns across all three. `rt_stats 1,2,3`, `rt_stats 1 2 3` and `rt_stats 1, 2, 3` are the same thing, `rt_stats 0` hides the readout, a bare `rt_stats` reports which panels are on, and anything else prints the usage. The selection lives in the archived cvar `rt_stats_panels` (a change to it takes effect on the next frame), named that way because a cvar called `rt_stats` would have shadowed the command — `Cvar_Command` runs before the command table is consulted. A second command, `rt_stats_dump`, writes every number of the current frame into `qperfdump.log` in the game directory, one `section name value` line per number and appended rather than overwritten so successive runs can be diffed. Formatting and the write happen on a detached thread over a copy of the snapshot, so a dump costs the frame nothing and cannot be seen in the numbers it records.
- **The frame reports how many renderer entry points it made** — every `rg*` call the host makes runs through the same two `Call<>` overloads in `vkpt.cpp`, and some of what they do before dispatching is not free (the suspended test alone used to end in a driver query), but none of it was visible in a profile: the pass timings cover the GPU and the `rt_stats 3` slots cover the host code around the calls, not the surface itself. `RgFrameStats` gains `apiCalls`, counted in both `Call<>` overloads with a relaxed atomic increment, reset at `rgStartFrame` (so the number belongs to the frame just recorded, including the `rgStartFrame` that opened it) and read in `rgGetFrameStatsEx`. It is printed by `rt_stats_dump` as `gpu.calls rg entry points` and drawn by the `rt_stats 1` panel as a `CALLS` row under the ray counters. It is a count and not a duration, so it only becomes a cost when multiplied by what the entry point does before it returns; with the surface query below cached, that per-call remainder is a lock, a map lookup and a `VulkanDevice` call.
- **`rt_cluster_dlights`, a switch for the dynamic lights in the cluster lists** — a moving emitter could be seen to change the frame time of the whole scene: a lava ball that leaves the lava near the camera took the `clusters` slot of the CPU profile from a fraction of a millisecond to nearly 200 ms while the number of traced rays barely moved, and the same happened on maps where nothing of the sort was visible nearby. The lists are built from the lights the frame registered, and a dlight, a sprite or a moving emissive model is such a light, so one of them appearing or leaving changes the *set* the lists were built from — and a dlight is named by its slot, so a shot or an explosion changes that set on the frames it lives and dies on, whatever else the frame holds. The new cvar, default `1`, gates only the registration of those three families into the cluster lists (`gl_rmain.c` dlights, `r_sprite.c`, `r_alias.c` model lights and the moving emissive polys of `r_world.c`); the light itself is still uploaded and still lights the scene, it is simply not offered to the cluster lists, so `rt_cluster_dlights 0` is an A/B switch for whether a moving emitter can disturb the list composition of the frame. It is an experiment and is meant to be removed with the light module, which builds the lists in the renderer from the BSP tables and the light set instead.

### Fixed
- **The `fog` console command works again** — 0.9.1 removed the legacy `fog <density> [r g b]` handler because the name had been taken by the fog-volume editor, which left map scripts and mods unable to set fog at runtime. The two now share the name and are told apart by their first argument: a dash-prefixed option (`fog -v …`) is the volume editor, anything else is the classic form, which no volume option can look like.
- **A map with a skybox died on its first frame with `RG_WRONG_ARGUMENT`** — the skybox upload in `Sky_DrawSkyBox` never filled in its vertex count, and the API rejects empty vertex data (`Vertex data / count is null`, `UploadRasterizedGeometry`), so every map whose `sky` key named a set of `gfx/env/<name>{rt,bk,lf,ft,up,dn}` textures that the mod actually ships was unplayable — the error arrived before anything the level contained was drawn, and the six sky faces were the only indexed upload in the renderer that did not carry its count. Arcane Dimensions' start map is one of them (`"sky" "moonrise_"`, `gfx/env/moonrise_*.tga`), which is why switching to `ad` failed while the classic skies of `id1` still worked: those leave `skybox_name` empty and take the scrolling-layer path instead.
- **The water and animated surfaces of a world texture no longer take one upload each** — the chain loops of `R_DrawTextureChains_Water` and `R_DrawTextureChains_Animated` decide whether the next surface continues the current batch or opens a new one with a comparison left over from the rasterizer, and its alpha term has the sign inverted: `lightmap_tex != last.lightmap_tex || fabsf(alpha - last.alpha) < 0.001f`. The second half is true for every surface whose alpha is the *same* as its neighbour's, so a chain is cut at nearly every surface boundary — measured on Arcane Dimensions' `ad_mountain`, 669 uploaded geometries in one frame where the surfaces of a texture could have shared five, at 8–20 µs each (`rgUploadGeometry`) — while the first half asks about the lightmap page, which the ray-traced upload of a batch never reads: it selects the material from the surface's own textures, and no per-surface state is taken from the page. Read the other way, the same test merged surfaces that agreed on nothing but the page and handed all of them the alpha and the flags of the last one. The split is now `RT_UploadStatesMatch`, which compares every field the upload of a batch reads — entity, model, material textures, alpha, alpha test, zbias, and the warp/water/acid/animated flags — and a teleport surface always opens a batch of its own, because its portal is resolved into the uploaded geometry; what stays per surface travels inside the batch instead (vertex range, unique id, cluster, packed light styles, written by `RT_BatchSurface`). The cvar `rt_world_batch_merge` selects between the two, `1` for the state comparison and `0` for the historical test, and it defaults to `1`; the picture is meant to be identical either way, so a water or animated surface that renders differently under `1` is a bug worth reporting rather than a reason to keep `0`.
### Changed
- **A light that appears or disappears no longer composes the whole map** — the cluster light lists are handed back for as long as the frame brings no light the lists do not hold and leaves out none of the lights they hold, and every other frame ran the full composition: the PVS walk of every light over every cluster it can see, with a reach pass over all of them. The path that avoided it covered the lights that *moved* only, while the frame a light is born on or dies on is a change of the *set* — which is the frame the CPU profile showed as a fifth of a second in `clusters` when a lava ball near the camera started to glow, when a shot was fired, when a rocket trail left a dlight behind, and when an emitter stopped being drawn. The lists are kept through such a frame now: a light that leaves gives every slot back and the place it held stays in the sources as a place that holds no light and that no slot names, a tombstone, which the walk of the next frame passes over and which the light that appears takes — so the places of the lights that stayed are still the places their slots name them by, and not one list of the scene changes for them. Only the clusters the changes reach are looked at again: pass one takes the slots of the lights that moved back and grants them again from where they stand, the lights that appeared are granted from theirs, and pass two chooses the top-up set of the clusters those lights reach anew, with the grid of that pass rebuilt for them (`ClusterLightLists::UpdateSourceSet`). The frame declines the work where a composition is the better answer and says so by returning: when the lights that changed are half of the set or more, when the places held for lights that left grow past a quarter of the set and past a handful of them, or when the frame's own accounting does not add up. A composition compacts those places, because it takes the frame's set for its sources outright, so they never accumulate over a map. The counters of the `clust miss` row of `rt_stats 3` (and `cpu.cluster miss set` / `miss move` / `miss other` in `rt_stats_dump`) count the frames that *composed*, so the light that appears on a frame of `rt_cluster_incremental 1` no longer moves them — which is the way to see that the spike is gone, together with a `clust lists` row that stays where the other frames put it. `rt_cluster_incremental 0` keeps the all-or-nothing behaviour and composes on any change to the lights exactly as before.
- **The CPU profile says what the cluster lists cost apart from what surrounds them** — `rt_stats 3` measures `clusters` over the whole `RT_ClusterLightListsUpload` call, and the rows under it were the four parts the renderer hands back (`clust vis`, `clust topup`, `clust fill`, `clust upload`) plus `clust resolve`, so the largest row of the panel could not separate the leaf lookup, the lists themselves and the two getters that follow it (`rgGetClusterLightStats` and `rgGetClusterLightGrants`): `clusters` − `resolve` − those four was the only way to see the remainder, and nothing printed it. Two of the rows under it were worse than unaccounted — `clust pvs` and `clust walk` were the two passes of the host-side composer, which no longer exists in the host, and their slots were declared and drawn on every frame while nothing ever wrote them, so they read as two passes that cost nothing. `RgClusterLightStats::totalMs` — the whole of `ClusterLightLists::SetSources`, the publication included — is sampled into the `clust pvs` slot under the name `clust lists`, and `clust walk` is gone from the panel, from the dump name table and from the enumerators (`RT_PROF_CLUSTERS1` and `RT_PROF_CLUSTERS_WALK` become `RT_PROF_CLUSTERS_LISTS`, `RT_PROF_CLUSTERS2` becomes `RT_PROF_CLUSTERS_TOPUP`). The panel gained no row: `clust lists` is a row that was printing zero. A log parser that looks for `cpu.slot clust pvs` or `cpu.slot clust walk` needs the new name; `cpu.slot clust topup` keeps its value under the name it already had on screen.
- **A command-buffer reset and a 48 MiB clear no longer run where they have nothing to do** — `CommandBufferManager::PrepareForFrame` reset all three command pools of the frame slot on every frame, but only the graphics pool ever holds a command buffer: `StartComputeCmd` and `StartTransferCmd` have no callers anywhere in the tree, so those two resets were driver entry points on pools that were already in the state the reset would put them in — a pool that recorded nothing since its last reset has all of its buffers in the initial state. The reset is now taken only where the recorded count says something was recorded, which leaves the buffer handles, the submission order and the growth logic of `StartCmd` with exactly the numbers they saw before. In the same frame `VulkanDevice::Render` recorded a fill of the cluster light statistics — 50 331 648 bytes, 48 MiB, one of the three slots the adaptive light selection accumulates into (`LightManager::ResetLightStats`) — whatever the statistics were set to, and it sat in the `lights` row of `rt_stats 2`. At `rt_q2_lightstats 0` (`Q2_LIGHT_STATS_DISABLED`) neither side of the buffer runs: `q2AccumulateLightStats` returns before its first add and `q2SampleClusterLights` skips the read that would have used the value, so the fill only stored zeros. It is recorded now only when the mode consumes the buffer, and the `lights` row falls by it; the barrier that follows is kept, because it orders the light lists as well. The default `rt_q2_lightstats 1` records exactly the same commands in exactly the same order as before.
- **The driver is asked for the surface capabilities once a frame instead of once per API call** — `VulkanDevice::IsSuspended()` runs at the top of every `rg*` entry point and ends in `Swapchain::IsExtentOptimal()`, which asked the driver for the surface's capabilities (`vkGetPhysicalDeviceSurfaceCapabilitiesKHR`, the only way to know the current extent, the image count range and the usage flags) on every one of those calls. That is a driver round trip: measured in isolation on an RX 9070 XT it costs 11.1–13.4 µs, against 0.013 µs for the same test with the query taken out, so the frame was paying microseconds per entry point and none of it appeared in any slot of `rt_stats 3` — the cost landed in the host code around the calls, spread thinly over the whole frame. The answer is cached in `Swapchain` now (`cachedSurfaceCaps` together with the `VkResult` that produced it): `AcquireImage` and `Present` invalidate it, `GetSurfaceCapabilities` queries only when it is invalid, and a failed query leaves it invalid so the next caller retries instead of reading a struct the driver never wrote. The steady state is one query per frame, taken at the frame boundary where the swapchain decides whether its extent changed; `Create` and the out-of-date branch of `Present` drop the cached block first, so a swapchain is still built and a resize is still decided against the surface as it is at that moment. Every reader (`IsExtentOptimal`, `GetOptimalExtent`, `Create`) goes through `GetSurfaceCapabilities`, which is the only function that talks to the driver, and nothing about the extent, the image count, the present mode or the vsync decision changes. Only `VulkanDevice` and `Swapchain` are affected; the host-side API is untouched.
- **The GPU timing panel now splits the display-resolution tail** — the GPU panel (`rt_stats 2`) reported one `upscale` line over the DLSS/FSR pass together with the blit into the effects buffer, one `post` line over CAS sharpening together with bloom and every post effect, and one `present` line over the HUD rasterization together with the final blit into the swapchain. That is the part of the frame the ray-traced passes do not cover, so the panel could not say which of those steps was paying for itself: `fsr` settings that cut the ray count by a third moved the frame rate far less than the ray savings predict. Three marks are added (`PassTimings`, `VulkanDevice.cpp`), taking the pass count from fifteen to eighteen: `upsblit` (the upscaled image blitted into the effects buffer, apart from the upscaler that produced it), `sharpen` (the dedicated CAS/naive pass, apart from bloom and the post effects, which keep the `post` line; when CAS is selected together with FSR2 or FSR3.1 it runs inside the upscaler instead and this line stays at zero) and `swapblit` (the blit into the swapchain, apart from the HUD rasterization and the wipe/CRT effects, which keep the `present` line). The panel is driven by `RG_GPU_PASS_COUNT` and needed no change beyond it.
- **The shadow-ray counter is split by the pass that casts the rays** — `rt_stats 1` reported one `SHADOW` category, and it could not be read against the pass timings: the pass named `shadow` in `rt_stats 2` is the god-rays section (the sun's shadow map together with the shafts marched through it), so its ~1.1 ms had nothing to do with the ~26 million visibility rays the counter showed, and nothing said whether those rays were paid for by `direct` or by `indirect` — a question that matters, because together those two passes account for about 35 ms of a 56 ms frame. The category is now two, `SHADOW DIR` from the NEE rays of the direct pass (`RtRaygenDirect.rgen`) and `SHADOW IND` from those of the indirect pass (`RtQ2Indirect.rgen`), which is where the split actually is: the second bounce samples the cluster's lights exactly as the first one does, so its visibility rays are counted with it. `RAY_STATS_CATEGORY_COUNT` goes from four to five, which is the only number that had to move — it sizes the counter buffer, its descriptor range and the per-frame read, and `RG_RAY_STATS_CATEGORY_COUNT` follows it under the `static_assert` in `GetFrameStatsEx`. The dump gains the line `gpu.rays shadow ind` beside `gpu.rays shadow dir`, and the counter panel gains the row `SHADOW IND`; nothing else about either readout changes. The values themselves were never in doubt: every `rayStatsAdd` call site is guarded by a traced-ray test, so a category only counts a ray that was really cast.
- **The `shadow` GPU pass is named `godrays`** — it was the one label in the pass table that named something other than what it measured: the span between the marks covers the sun's shadow map and the volumetric shafts marched through it, so `shadow` read as if it were the price of the visibility rays the direct and indirect passes cast, and in one 4K run that was 26 million rays against the 1.1 ms printed below them. Nothing about the pass changed — the same two marks, the same position, the same cost — only the name the panel and the dump print, and the enumerator behind it (`GPU_PASS_GODRAYS`, which was `GPU_PASS_SHADOW_GODRAYS`). A dump or a log parser that looks for `gpu.pass shadow` needs the new name; the values around that line are unchanged.
- **The renderer switch is gone** — the video menu's `Renderer` row and the `rt_classic_render` cvar behind it offered a choice between `Ray Traced` and `Classic`, but there was never a second renderer to switch to: the cvar turned on the classic *lighting* path inside the ray-traced pipeline (the dynamic-light marking and lightmap uploads of `R_PushDlights` / `R_RenderDynamicLightmaps` / `R_UploadLightmaps`, the brush-model dynamic lights, and the `lightmapEnable` / `lightmapLayer` shader branches that shaded the world from the lightmap texture), while the composite kept showing the ray-traced image either way — which is why switching it changed neither the picture nor the frame rate. It is all removed: the cvar, the `rt_pfnswitch` command, the menu row, `RgDrawFrameLightmapParams` with its `pLightmapParams` frame field and the `lightmapEnable` / `lightmapLayer` fields of `ShGlobalUniform`, the host functions behind them, and the classic-only dlights of rockets and explosions (in the ray tracer an explosion lights the room through the emission of its own sprite). Every one of those paths ran only at `rt_classic_render 1`, so the default `0` path renders exactly as before — what went away is the dead work that setting used to enable.
- **`rt_pass_stats` and `rt_prof` are gone** — both were folded into `rt_stats`, and no alias is kept: `rt_pass_stats 1` is `rt_stats 2` and `rt_prof 1` is `rt_stats 3`. A config file or binding that still names them now prints an unknown-command message and changes nothing, so replace them with `rt_stats 2` and `rt_stats 3` respectively.
- **The sun and its god rays are ten times dimmer again** — the fraction of the light fixup a sun takes (`RT_SUN_LIGHT_INTENSITY_SCALE`, next to `RT_FIXUP_LIGHT_INTENSITY` in `glquake.h`) goes from a tenth to a hundredth. It is one constant applied to the colour before the light is uploaded, so everything that reads that colour follows it by exactly the same ten times: the direct sunlight, the indirect sun (`rt_sun_bounce_range` / `rt_sun_bounce_scale`) and the god rays, whose inscatter is that colour scaled by `gr_intensity`. The shafts keep their proportion to the sunlight they are made of — that ratio is the calibration, so no second multiplier was added for them. Nothing else moves, because nothing else reads the light: the drawn sky and its disc are painted from `rt_sky_color`, the sky's ambient (`rt_sky_brightness`) and the fog's light (`rt_volume_lintensity * rt_brightness`) are unchanged, and `gr_intensity` still scales the shafts on top. `rt_sun` remains the multiplier in front of the fraction, so **`rt_sun 10` restores the previous brightness exactly** while `rt_sun 0` still switches the light off. One value is now an order of magnitude out of step with the sun beside it: `rt_volume_lintensity` (default `250`) lights the fog without ever reading the sun, so it may want to come down with it.
- **The cluster light lists are handed to the GPU once per composition instead of once per frame** — `LightManager::SetClusterLightLists` ran on every frame and did the whole job every time: it cleared the 8193-entry offset table, copied the new offsets over the prefix, resolved every word of the lists through the light registry (one hash lookup for each of the up to a hundred thousand entries, however few lights they name), wrote the words into the staging buffer and had `AutoBuffer` copy both buffers — the offsets and up to four megabytes of words — into device-local memory. The composer above it already refills its lists only when the frame's light set changed and otherwise reuses the composition bit for bit, so on a reused frame all of that produced exactly the words the device had been given a frame or two earlier. The composer now numbers its compositions: `ClusterLightLists` carries a `listGeneration` that is bumped by `Reset`, by `PrepareTables` and by `FillLists` — the three places that materialise `offsets` and `list`, of which `FillLists` is the only one that writes the words — and the number travels with the publish call. `LightManager` records the order in which the frame registered its lights (`AddLight` appends the id, so the order *is* the mapping from id to array index, and the id→index map is written by the same calls), and keeps a per-slot note of what that slot's device buffer already holds: generation, cluster count, word count and registration order. A frame publishes only when its note does not match; on a match the slot's buffers already hold these words, and both the resolve and the copy are skipped. The note is per frame slot because the buffers are: two frames are in flight, and a slot that has never been given a composition must publish even while the other slot holds the identical words. Nothing about the picture depends on the cache — the tests are the identity of the composition and of the light order, not a comparison of the words — and what it removes shows in the `clust upload` and `clusters` rows of `rt_stats 3` and in the `CALLS` count, since on a hit the frame compares a few hundred ids against the hundreds of thousands of entries it used to resolve.
- **The map's emissive lights are re-registered without re-asking which entity lights reached them** — the per-frame re-registration of a map's stored emissive lights (`RT_UploadAllWorldModelLights`) scaled every one of them by the lightstyle values of the surface it came from, and before applying a value it tested the light against the reach of `rt_light_styles`: a nearest-entity-light query per lightstyle the surface carries, and that query is a linear scan over every entity light of that style with a vector length per entry. On a map like Arcane Dimensions' start that was hundreds of stored lights times up to four styles of scans, every frame, to answer a question whose answer changes only when the light set or `rt_light_styles_reach` does. The answers are now built once (`RT_BuildWorldLightStyleAcceptance`) and rebuilt only when the stored list is collected again or the reach cvar moves, so a frame reads a byte per style; the lightstyle *value* is still read per frame, which is what makes a flickering lamp flicker, and the scale it produces is the same one. `RT_TexturedAreaLightCenter` also left the per-frame path: a stored light does not move, so the center it is placed by is derived where the light is collected. Everything else about the registration stays — the lights are still uploaded and still registered into the cluster lists every frame, because a frame's light array is built from the additions of that frame and a light missing from it leaves a hole in every cluster list naming it. The upload is also handed over in one call (`rt_wmodel_lights_batch`, default `1`: `rgUploadTexturedAreaLights` for the whole map instead of a `rgUploadTexturedAreaLight` per light; the per-light cost is the call, not the light) — set it to `0` for the per-light path.
- **The alias models no longer trace a light point per entity** — `R_SetupAliasLighting` walked the BSP from the entity to its leaf and ran the classic lightmap recursion for every visible model, inside the parallel entity pass and under that entity's own mutex, to produce a shade vector and a light colour that nothing reads: the ray-traced path takes the lighting of a model from the lights it registers for it, and both values were only ever passed to `GetPoseVertices`, whose parameters the function never looks at. The function, its call site, the two parameters the vertex path ignored and the `r_fullbright` cheatsafe overrides that rewrote nothing but that colour (half grey, or white when `r_fullbright` was on) are gone; the parts of those modes that do reach the picture here — the white texture and the forced alpha of `r_lightmap_cheatsafe` — are untouched, so `r_fullbright 1` and `r_lightmap 1` render as before. The classic lightpoint builtin of the QC VM (`getlight`) was the other caller and is unaffected apart from now being the only one.
- **A light that stays where it is no longer resolves its BSP leaf again every frame** — the frame hands the cluster composer one entry per registered light, and for each of them it asked which leaf the light stands in, because that leaf is what turns into the cluster the light is filed under. The question was put to the map every frame (`Mod_PointInLeaf`, a BSP descent per light), and a light whose origin sits inside solid geometry — a wall torch, which is most of the map's lights — was probed from up to eighteen points out to twenty-four units before one of them answered with an open leaf. None of that changes while the light stands still: the descent reads the light's origin and the map and nothing else. The answer is kept per registry slot now, keyed by the light's identity and its origin — never by the slot number, since a slot is handed to whatever registers into it next — and the descent is made only when one of those changed. What the frame emits is deliberately not cached: the source entries are still written every frame through the same leaf-to-cluster mapping, with the same id, origin, cluster and reach, so the composer is given the same bytes it was given before and the picture cannot depend on the cache. The map itself is part of the key (the world model, its leaf array, its leaf count and the parse revision of the entity light file), because a new level can be loaded onto the very addresses the previous one occupied. The `clust resolve` row of `rt_stats 3` is what moves; it is a per-second maximum, so a single frame in which something really moved still shows up there.
- **The entity lights of a map are indexed by light style instead of rescanned whole** — `RT_NearestStyledLightDistance` answers how far the nearest entity light of a given light style stands from a point, and the map's stored emissive lights ask it once per light style they carry, every frame, to decide whether a light style of `rt_light_styles` is near enough to scale them by. The query walked every entity light of the map and compared its style per entry, so on a map with 1476 entity lights — Arcane Dimensions' start — a stored light with four styles paid four full scans of 1476 entries, each entry a subtraction and a `VectorLength` that ends in the CRT's `sqrt`, and that was the bulk of the `wmodel lights` row of `rt_stats 3`. The entities are now bucketed by style once (`RT_BuildStyledLightIndex`, a counting sort over `MAX_LIGHTSTYLES`), rebuilt lazily whenever the entity light parser has run again (`rt_elights_revision`), and a query walks only the entries of the style it was asked about — in ascending source order, so the nearest distance is the same number the full scan produced. `RT_ClusterLightAdd` loses the other scan: the registry is asked once per light per frame whether the light it was handed is already in it, so a 4096-entry table now remembers the slot each light id was last registered at, the id comparison is what validates the slot (a stale or colliding entry falls through), and the linear scan stays as the fallback that fills the table. Neither change touches what is registered or in which order, so the composed lists are the same bytes.
- **A dynamic model whose geometry did not change is not built into an acceleration structure again** — every piece of dynamic geometry a frame collects (a door, a monster, a projectile, a batch of particles) is added to the frame's vertex collector and then built into the dynamic bottom-level acceleration structure of its filter, and that build ran every frame whether or not anything in it had moved. The build's price is the geometry it covers, so a door standing still, a monster holding a frame or a corpse lying on the floor paid it for nothing, in the `Building dynamic BLAS` section of the frame. The build input is now hashed as it is collected (`HashDynamicGeometryInput`: the positions of every vertex, the indices and the transform of each geometry handed to `AddDynamicGeometry`, into a per-filter hash the frame seeds) and compared against the hash that the slot's acceleration structure was built from (`HashDynamicBLASInput`, which also covers the geometry set and its order, the build ranges, the primitive counts and the structure's handle, so a recreated one is never mistaken for an up-to-date one) — a structure that already describes exactly this geometry is left alone. The geometry count is still set before the decision, because an empty structure is not added to the top-level one and the count is read either way. The hash is kept per frame slot, since the structure a slot builds into is the one built for the same slot two frames earlier. What the shaders read is untouched: the dynamic vertices are still copied out of the staging buffer every frame and the geometry info is updated as before — the hash only answers whether the build has anything to do.
- **The view model row of the CPU profile can be read again** — the `viewmodel` row of `rt_stats 3` brackets the whole view model task, and that task does not only draw the gun: after `R_DrawViewModel` it calls `RT_UploadAllElights`, `RT_UploadAllWorldModelLights`, `RT_UploadAllTeleports` and `RT_ClusterLightListsUpload` inside the same bracket, each of which reports its own row (`elights`, `wmodel lights`, `teleports`, `clusters`). Because a slot keeps the longest sample of the window, `viewmodel` was a row that contained four other rows and was read as the price of drawing and uploading one alias model, which is the cheapest thing in the task. A new slot (`RT_PROF_VIEWMODEL_DRAW`, printed as `vm draw` and dumped as `cpu.slot vm draw`) brackets `R_DrawViewModel` and the two debug draws beside it, so the draw is a number of its own and what `viewmodel` is left holding is the four uploads that follow it in the same task (a slot keeps the longest sample of the window, so such a row is not the sum of the rows inside it). The comment above the slot enum now states that a slot may contain others and that such rows must not be added together. Nothing about the frame changes: the bracket is empty work when the profiler is off.
- **The colour settings are re-parsed when they change instead of on every read** — the getters behind `rt_sky_color`, `rt_sky_clouds_color`, `rt_light_color` and `rt_globallight` compared their cvar's text against the text they had parsed last (`strcmp` in `RT_ColorGet`, `Quake/gl_vidsdl.c`), and the light paths call them once or twice per light per frame: `rt_light_color` alone is read by the fixup that every entity light, dynamic light, world-model light, sprite and alias light goes through on its way to the renderer, which on a heavy map is well over a thousand calls a frame. The comparison is gone: each setting watches its own cvar through `Cvar_SetCallback` and re-parses on the callback, which `Cvar_SetQuick` fires after every change that took (a `set`, a `reset`, a menu row or a config file), so the value — and the complaint about a value that does not parse — follows the setting rather than the frame rate. The cache deliberately does not key off the string pointer: `Cvar_SetQuick` reallocates only when the length changes and otherwise writes into the buffer it already has, so the pointer survives a change and would have hidden it. The first read still parses, which is what the designators in the table say. Behaviour is unchanged: the same accepted syntax, the same fallback to the default when a value does not parse, and the error line is still printed once per change rather than once per frame.
- **Texture and cubemap descriptors are written only for the slots that changed** — `TextureManager::SubmitDescriptors` and `CubemapManager::SubmitDescriptors` ran every frame over every slot they own — `maxTextureCount`, 4096 by default, plus the 32 cubemap slots — and asked each one whether its descriptor still held what had been written to it, although a slot changes only when a material is created or destroyed or when the dynamic sampler filter moves. The two managers keep a list of the slots whose descriptor is not yet written for each frame in flight, because each frame in flight has a descriptor set of its own: every slot is listed once at construction (the sets are allocated with undefined content), a slot is appended by the two places that write it (`InsertTexture` and `DestroyMaterialTextures`, `CreateCubemap` and `DestroyCubemap`) and by the sampler-recreation branch, which needs every slot again, and the per-frame loop walks that list, which is empty on a frame where nothing changed. `vkUpdateDescriptorSets` is not called at all then, so a frame that creates no material now makes one driver entry fewer. `Swapchain::IsExtentOptimal` stopped copying the cached `VkSurfaceCapabilitiesKHR` on every entry point too: the extent test is made once where the query succeeds and the per-call path returns the stored answer, with the surface-lost and failed-query outcomes unchanged (a failed query is still not cached, so the next caller retries). What is written, in what order, and with what values, is the same on every path; only the per-frame scan is gone. A slot is marked more than once between two submits on the paths that exist — the constructor lists every slot before the first texture has been created, and each of those textures is marked again by its own insert — so the list carries a byte per slot saying whether it is already pending, and a repeated mark is dropped. Without that, the list grew one entry per mark rather than one per changed slot: on the first frame of a map, where the cache is cold and every slot is written, the entries past the `maxTextureCount` that the batch holds were duplicates of slots that had just been written, and they reached the `assert(0)` in `TextureDescriptors::UpdateTextureDesc`, which tested the batch for room before it tested the write cache. `UpdateTextureDesc` also flushes the batch when it fills now, so a caller that marks more slots than the batch holds gets two `vkUpdateDescriptorSets` calls rather than a failed assertion; the descriptor set receives the same writes either way.
- **The particle pass stopped repeating per-particle work once per vertex** — `R_DrawParticlesFaces` writes three vertices for every particle in the active list (four with `QUAD_PARTICLES`, which is compiled out) and did two things once per vertex that belong to the particle and not to the vertex: it packed the particle's colour out of its palette entry into `packedColor` for each of its vertices, and it built the up- and right-offset positions with `VectorMA` into temporaries which were then copied into the vertex field by field. The colour is packed once per particle now, and the two offset positions are computed straight into the vertex field — which is the same arithmetic in the same IEEE order, minus two of the three packs and two `VectorMA` calls with their round trip through a temporary, per particle. The drawn-particle counter is advanced once for the whole batch instead of once per particle: the add is still the atomic one, so the pass stays correct if it is ever run as a task, and nothing observes the counter while the particles are emitted — it is zeroed before the frame (`gl_rmain.c`) and the `r_speeds` readout never printed it. The vertices handed to `rgUploadRasterizedGeometry` are byte for byte the ones of before — the same positions in the same order, the same texture coordinates, the same packed colour, the same zeroed fields the shader reads as zeros — so the picture is untouched; what goes away is on the order of a tenth of a millisecond of a frame that is otherwise bound by the GPU.
- **A registered light costs one flat probe instead of two hash lookups and a node** — the registry that maps a light's unique id to its place in a frame's light array was an `rgl::unordered_map` per frame slot, and the frame asked it three times over: `AddLight` asked whether the light had been registered already, `FillMatchPrev` asked where the same light stood in the previous frame, and `SetClusterLightLists` resolved every word of the light lists through it — one lookup per word, for the hundreds of thousands of words a thousand lights fill the clusters with. The map is also emptied at the top of every frame, which walks its nodes, and every registered light allocated a node and hashed its id into it. The registry of a frame slot is a flat table now (`LightManager::registry`, `LIGHT_REGISTRY_SIZE` = 8192 open-addressed entries of sixteen bytes: the generation of the frame that wrote the slot, the place in the light array and the id), so `AddLight` probes once and reuses the slot it landed on for both its lookup and its write, and `FillMatchPrev` takes the ordinal the frame registered the light in: while the light set of the scene does not change — which is almost every frame — the previous frame's registration order names that same light at that same ordinal and its previous place is read out of the table directly, and only a light that is new, or that moved in the order, falls back to a probe of the previous frame's registry. Emptying a registry is a generation bump rather than a walk: an entry of another generation is refused on its first read and is exactly what an empty slot holds, so the table is only ever written over, and it is cleared in whole when the 32-bit counter wraps. The counters start at one, because generation zero is what a table no frame has written holds. What is registered, in which order, and with which place is unchanged — the order is appended by the same `AddLight` calls that write the registry — so the words the composer publishes and the two match tables that map the previous frame's light places to this frame's are the bytes they were before. The resolve loop keeps a cache of its own (2048 open-addressed slots of `uid` → place, larger than the registry so the table stays sparse), so an id is resolved once per publication instead of once per word. One published word changes: an id the frame did not register resolves to `LIGHT_INDEX_NONE` instead of `0`. `0` is the directional light slot, and every reader of the lists tests a word against the regular-light range before it uses it, so nothing visible follows from the change — but the old word was a definition that held only as long as every reader kept making that test.
- **The light words and the light statistics are cleared only as far as the lists reach** — two clears in the light path covered ranges nothing read. `SetClusterLightLists` filled the staged word buffer with four megabytes of zeros before it wrote the words it had resolved, and had the whole buffer copied into device-local memory, although only the prefix the offsets delimit is ever read back: the words are written and the copy is made over that prefix now, and only on a frame that publishes; the length of that copy is the word count that publication recorded for its own frame slot (`publishedListWords`) and not the count of the last publication, because a publication is copied two frames after it was made and by then the other slot has published a count of its own — a shorter one would leave the words past it as the other slot's copy left them, and a cluster inside the prefix this slot's offsets delimit would be handed lights of another frame's composition. `ResetLightStats` cleared a whole 48 MiB statistics slot at the start of every frame — the counters of every cluster the frame's lists do not reach — and it clears only as far as the published cluster count now, which on a map whose lists stay inside a fraction of the cluster grid is a fraction of the slot; a slot whose fill already covers the clusters the lists can reach is skipped, since it is handed back by a frame rotation anyway, and the target stays the whole grid until a composition has been published (`LightManager::Reset` returns it there). What the shaders read is the same memory with the same contents: a cluster no list names has no counter any reader could reach.
- **The per-face work of the world submit is cached where its answer cannot change** — three questions were asked of every face of every submit, and all three are answered by the map or by the model rather than by the frame. `RT_PackSurfaceLightStyles` resolved the light-style pack of a face from scratch: the canonical light texture of its texture, the centroid of its vertices, the entity transform, and up to four scans of a light-style bucket with a square root each (`RT_NearestStyledLightDistance`) — on Arcane Dimensions' `ad_mountain`, 21 763 distance scans per full sweep of its 25 250 world faces, paid again on every re-submit of the world and on every frame for its 615 water faces and for every face of a brush entity. The pack is a table lookup now: the faces of the world are indexed by their surface, and the faces of a brush entity — which cannot be found by their index, and whose reach answer follows the entity — sit in a 512-entry direct-mapped table keyed on the entity, the surface, its base texture, the whole transform and the two cvars the answer depends on. The answer is the same because nothing else is read: the face's base texture (`texinfo->texture`, not the frame of its animation), the styles the BSP gives the face, the positions of the styled lights, which only a map load changes, and those two cvars. The table is sized off the map in the same reset the brush cluster cache uses — which runs at map load, before the first world submit and before the lights are parsed — and the entity table is cleared in whole there, so a face of the previous map is never answered out of this one. `RT_SurfaceOwnedBySubmodel` walked the submodel table once per face: of the 25 250 faces of that map, the 19 376 that belong to no inline submodel each walk its 392 rows, around 7.6 million comparisons per pass, paid by the emissive collection and by the world light upload. It is a bitmap built at map load now, with the walk kept as the fallback for a map whose table was not built, and the predicate behind it is the one the walk tested. The water chain computes the animated diffuse texture and the canonical light texture of a chain once per texture rather than once per face, since both name a property of the texture and the frame of the animation is fixed within a frame. What the frame saves is on the order of a tenth of a millisecond of a frame that is bound by the GPU; the structural saving is at map load and at the world re-submit, where the ownership scan alone is around nine milliseconds.

- **The cluster light lists are rebuilt incrementally by default** — `rt_cluster_incremental` shipped as an experiment and defaulted to `0`, and at `0` the path it enables could not be taken at all. A quiet frame is served by the reuse branch, which publishes the previous composition as it stands — but the branch also cleared the composition order whenever the cvar was off, and the incremental branch is entered on that flag being set from the frame before. So the composer could never tell a frame whose light set is the one the lists were built for from a frame it had to build again: every frame on which any light moved, gained a leaf or lost one re-ran the whole map, one PVS row per light, which is the ~23 ms `clusters` row of `rt_stats 3` that reappeared every third frame of a still scene while `clust cache` read 63% of its window. The default is `1` now, and the incremental path is what a frame with moved lights takes; `rt_cluster_incremental 0` restores the old behaviour as an A/B switch, since the two produce the same *kind* of picture but not the same words — a light that takes the place of another in a full list is chosen by insertion order, which a rebuild of one light's own slots does not reproduce. Two things had to be right for the path to be worth having. The records the frame is compared against hold the origin each light's slots were granted from, and are moved forward only for the lights that are granted their slots again: they used to be overwritten with the frame's own positions on every reused frame, which meant a light that walks never left the quantum its records were measured from — its lists would have been kept forever, with the drift of every step of the walk hidden under the record of the last frame. And a frame on which most of the lights moved composes in full rather than patching, because taking a light's slots back costs a walk over every cluster of the map while the composition costs one PVS row per light; the gate is half the registered lights. The reasons a frame is *not* served by the lists it has are counted apart now, and the two counters that named a leaf and a geometry are renamed for what they measure: `clust miss set` (the light set changed), `move` (a frame that was composed *because* its lights had moved or changed their leaf, so with the incremental path on it is the path declining the frame or the cvar switched off, not a light moving) and `other` (a new map, a new top-up reach, or a frame the incremental path turned down for another reason), drawn by `rt_stats 3` and dumped as `cpu.cluster miss move` / `miss other`. This path had never run before, so the first frames after this change are worth looking at with `rt_stats 1,2,3`: a scene that is still should read `clust cache` near 100%, a scene with lights moving should keep it there, and the `clusters` row should stay in the fractions of a millisecond instead of spiking to the tens.

## v0.9.1

### Added
- **`gr_intensity`** — the volumetric sun shafts were a fixed strength: the host hard-coded the value the shader multiplies its inscatter by, so how much sunlight is in the air could only be changed by editing `VulkanDevice.cpp` and rebuilding. It is a console variable now, beside the `rt_godrays` switch: `1` is the look the shafts were calibrated to, `2` doubles them, and `0` takes them out of the frame entirely — the shadow map they are marched through is not rendered then either, which is upstream's own test (`god_rays.enable && god_rays.intensity > 0`, `god_rays.c`). It reaches the renderer as a new field of `RgDrawFrameSkyParams`, beside the `godRaysEnabled` switch. The knob is Q2RTX's `gr_intensity` under this engine's own `rt_` naming and it means the same, but the two values are not comparable: Q2RTX multiplies its accumulated sun-disc radiance by this value, this one multiplies the directional light colour.
- **The sun's reach into an indirect bounce is a setting again** — the distance falloff that keeps indirect sunlight out of dark corners was pinned to Q2RTX's `pt_sun_bounce_range` default of 2000 units, and its `sun_bounce` multiplier was never ported at all, so neither side of that trade could be compared without editing the shader and rebuilding. Both are console variables now: `rt_sun_bounce_range` (default `2000` Quake units; `0` turns indirect sunlight off) and `rt_sun_bounce_scale` (default `1.0`, the physical value), matching upstream's own two cvars. They reach the renderer through one `vec4` of the shared uniform (`ShGlobalUniform.sunBounce`) so the std140 layout stays byte-exact — a single scalar there would shift every field behind it — and they affect the indirect pass only, since the direct pass never read either value. Like upstream, they are console settings and not menu rows.
- **Reflection and refraction depth of 4 and 8 bounces** — the `Reflections` row in the effects menu was clamped to `0-2` by `VID_Menu_StepFloatCvar`, so the values Q2RTX exposes for `pt_reflect_refract` (`0`, `1`, `2`, `4`, `8`) could only be reached by typing `rt_reflrefr_depth` in the console. The row now steps through exactly that set — shown as `off`, `1 bounce` and `N bounces` — and the host-side clamp on the uniform rises from `4` to `8` (`VulkanDevice.cpp`); the shader loops were already bounded only by that value. The shipped default of `2` bounces is unchanged, and the two new steps are per-pixel costs that grow with the depth, so they are there to compare against Q2RTX rather than to play with.

### Fixed
- **The sun disc in the sky was dimmer than the sky around it** — the procedural sky paints the disc as its intensity multiplied by the sky tint, with the intensity pinned at `25` and the tint at the `0..1` value behind `rt_sky_color` (about `0.25` at the shipped `32 0 64`, less at a darker one), while the atmosphere's own halo around it already arrives at an order of magnitude more. The sun therefore had no disc to speak of: the brightest thing over the horizon was the sky's Mie scattering, not the sun inside it. The intensity is `750` now, which reads as a sun at any tint, and the disc still takes the sky colour, so a dark tint gives a dark sky with a bright disc rather than a white one. It is painted into the visible cubemap only — the ambient and indirect sky are sampled from the disc-less one — so this adds no light source and changes nothing under the sky.
- **The god rays had stopped following the sun** — the entry below gave the sun the light fixup and divided it back out of the shafts' intensity so the shafts "kept the brightness they had". What they had was the brightness of a sun that lit nothing: the shafts are inscattered sunlight, proportional to the light colour exactly as in Q2RTX, so freezing them at the old value left a sun 8000 times brighter casting shafts 8000 times dimmer than the ratio that was originally tuned. They are proportional to the light colour again, and with the sun itself ten times dimmer (`### Changed`) they follow it: `rt_sun`, `rt_brightness` and the light tint all reach them, and `gr_intensity` scales them on top.
- **The sun reached the shading orders of magnitude below every other light** — the directional light was uploaded as `sky tint * rt_sun * rt_brightness`, with the sky tint arriving as the `0-1` value `rt_sky_color` holds, while every other source — dlights, the flashlight, the world and emissive lights — is pushed through `RT_FIXUP_LIGHT_INTENSITY` (`RT_QUAKE_LIGHT_AREA_INTENSITY_FIX * rt_globallight_mult * rt_brightness`). At the shipped `rt_sky_color "32 0 64"` the sun therefore entered `shade()` at about `0.13`, against the roughly `24000` a Quake light of intensity `300` arrives with — nearly two hundred thousand times brighter. Sunlight was invisible at `rt_sun 1`, and the indirect light the sun feeds only woke up at `rt_sun 100000` and above. That is why `rt_sun` read as an on/off switch rather than an intensity, and why the `rt_sun_bounce_range` / `rt_sun_bounce_scale` pair added earlier looked like it did nothing. The sun now passes through the same fixup as every other light, at a fraction of its strength (see `### Changed`), with `rt_sun` kept as the multiplier in front of it: `1` is a working daylight rather than an off switch (it is a light the scene is lit by, not one that is invisible against it), larger values overdrive it, `0` still turns it off, and the indirect sun and the god rays both scale with it. The drawn sky and its sun disc never read the light at all — they are painted from `rt_sky_color` — so neither is affected by it. One setting was tuned against the old magnitude and is worth re-reading against the new one: `rt_volume_lintensity`, the fog's own light (`250` by default), is never fed by `rt_sun` — it is lit by `rt_volume_lintensity * rt_brightness` alone — so it now lands next to the sunlit geometry rather than well below it. `rt_exposure_bias` is what pulls a brighter sunlit scene back down.
- **Grain in dark areas coming from the indirect pass** — Q2RTX fades the sun out of a bounce by the distance the bounce ray travelled (`pt_sun_bounce_range`, 2000 units: `sun_attenuation = square(clamp(1 - square(square(hit_distance / sun_bounce_range)), 0, 1))`, applied on every bounce and on the sun shadow ray that goes with it). Our port had no such range at all: a bounce that flew across half the map added its full share of sun energy and paid for its own sun shadow ray, which is what the "dense salt" in dark corners was made of. The attenuation is now evaluated exactly as upstream does it — on the first bounce (`sun_bounce_range *= 1 - sqrt(roughness)`, the scaling Q2RTX applies to its specular ray) and on the second bounce without that scaling — with `2000` as the range, which is upstream's default and not the `10000` of its reference-accumulation mode. Both numbers behind it are settings now (`rt_sun_bounce_range` and `rt_sun_bounce_scale`, see above), so this falloff can be traded for noise and cost without a rebuild.
- **The diffuse second bounce traced its own light sampling** — the indirect pass in Q2RTX runs `get_direct_illumination` (cluster light selection plus a shadow ray) only while `spec_bounce_index == 0`, i.e. on the first bounce; the second bounce is a single ray whose only light is the sun. Our second bounce re-sampled the cluster's lights and traced an extra visibility ray per pixel, which no Q2RTX build does, and each of those rays ran to completion even when the bounce had landed on a distant surface the first bounce never sampled. Removed — the second bounce now adds the attenuated sun and nothing else.
- **Low, Medium and High global illumination were the same setting** — the host enabled the diffuse second bounce as `rt_indir2bounces || gi_level >= 1.5`, and `rt_indir2bounces` is set to `2` in the shipped config, so the second bounce ran on **every** level: Low, Medium and High rendered the same image for the same price, and the menu row looked broken. The GI level alone now selects the bounce count (`enableSecondBounceForIndirect = gi_level >= 1.5`), which leaves Low at one bounce, Medium at one full-resolution bounce and High at two; `rt_indir2bounces` is still read so old configs load without an unknown-cvar warning, but it no longer forces the second bounce. Anyone who was running two bounces needs **`rt_gi_level 2`** to keep them.

### Changed
- **The sun is ten times dimmer** — the radiometric fixup the sun received (see the Fixed entries above) put `rt_sun 1` at the full strength of that fixup, and at that strength it overdrives a scene lit to Quake's own lamp levels. The upload now takes the same fixup at a tenth of it (`RT_SUN_LIGHT_INTENSITY_SCALE`, next to `RT_FIXUP_LIGHT_INTENSITY` in `glquake.h`): `rt_sun 1` lights the scene without washing out the lamps it shares it with, `rt_sun` is still the multiplier in front of it and `0` still switches the light off. Everything the sun feeds follows, because the scale sits on the colour before it is uploaded — the direct light, the indirect sun (`rt_sun_bounce_range` / `rt_sun_bounce_scale`) and the god rays, which read the same colour. The fog volumes do not: they are lit by `rt_volume_lintensity * rt_brightness`, which never read the sun. If the day now reads too dark, `rt_sun` is the knob to raise, not `rt_exposure_bias`.
- **`rt_nee_samples` default 2 → 1** — Q2RTX traces one light sample per pixel in the direct pass. Two samples stay unbiased (the estimator divides by the sample count), but they double the shadow-ray count of every direct-lit pixel, so the default now matches upstream and `2` remains available in the menu for anyone who wants the slightly smoother per-frame result. The value only affects the direct pass; the indirect pass never read it.
- **`readme.md` pointed at a `Tools/` folder that does not exist** — the game-data section told users to look for the material converters in `Tools/`, a directory that has never existed in this repository. The reference is dropped rather than left as a dead end.
- **The sky colour is one setting again** — `rt_sky_color_r/g/b` (what the sky is painted with) and `rt_sky_light_r/g/b` (what colour the sky light is: sun, sky ambient and god rays) were six archived cvars that had to be kept in step by hand, and `rt_sun_preset` wrote only the light triplet. They are replaced by a single console command, `rt_sky_color <r 0..255> <g 0..255> <b 0..255>`, which both tints the drawn sky and colours the light it casts (`rt_sky_color "32 0 64"` and `32,0,64` are accepted, and a bare `rt_sky_color` prints the current value and its usage). It cannot be just a cvar: `Cvar_Command` takes a single token, so `rt_sky_color 32 0 64` would never reach three channels — the value is stored in an archived `rt_sky_color` cvar behind the command, so it still survives a restart, and `rt_sun_preset` now sets the sky as well as the light that comes off it. The per-channel names are gone rather than redirected, so a config that still carries them reports them as unknown commands at start-up; the sky then comes from the archived `rt_sky_color`, whose default is the `32 0 64` those six cvars defaulted to, so the default image is unchanged.
- **The cloud colour is one setting too** — `rt_sky_cloud_color_r/g/b`, the colour the procedural clouds are composited over the sky with, are replaced by the command `rt_sky_clouds_color <r 0..255> <g 0..255> <b 0..255>` following `rt_sky_color` above: a bare `rt_sky_clouds_color` prints the current value, `"0 0 0"` and `0,0,0` are accepted, and the value lives in an archived cvar of the same name, so it survives a restart. The name follows the `rt_sky_clouds` switch that turns those clouds on. The three old names are gone rather than redirected, as with the sky above, and the default is the same `0 0 0` all three old cvars defaulted to, so nothing changes in the default image. The other cloud settings (`rt_sky_clouds`, `rt_sky_cloud_coverage`, `rt_sky_cloud_density`, `rt_sky_cloud_speed`) are single-valued and unchanged. All four colour settings share one implementation in `gl_vidsdl.c`, so a further merge is a table row.
- **The light tint and the global light colour are one setting each** — the same merge as the two above, applied to the remaining per-channel triplets: `rt_light_color_r/g/b`, the tint multiplied into every light source, is now the command `rt_light_color <r 0..255> <g 0..255> <b 0..255>`, and `rt_globallight_r/g/b`, the colour a light starts from before its own colour and the tint are applied, is now `rt_globallight`. Both accept the quoted and the comma-separated form, print the current value and their usage bare, and store it in an archived cvar of the same name, so the value survives a restart; the old per-channel names are gone rather than redirected. Both defaults stay `255 255 255`, so the default image is unchanged. They are read by the macros `RT_FIXUP_LIGHT_INTENSITY` / `RT_APPLY_LIGHT_TINT` and `RT_INIT_DEFAULT_LIGHT_COLOR`, which every light passes through once per light per frame; those now call a getter that re-parses the string only when it changed, so what a light pays per frame is one comparison of a short string rather than three conversions of the cvar's cached value.

## v0.9.0

### Added
- **Classic turbulent-surface warp** — the `*`-prefixed warp textures (lava, teleport) stood absolutely still in the ray-traced renderer. The classic engine animated them by re-rasterizing each surface into a small auxiliary image once per frame at an offset given by `WARPCALC` (`gl_warp.c`: `(s + turbsin[(int)(t*2 + cl.time*(128/pi)) & 255]) * (1/64)`, with `turbsin(x) = 8*sin(x*pi/128)`; the reference fork evaluates the same displacement in `cs_tex_warp.comp`), and that rasterization does not exist here, so a lava pool read as a flat painted texture. The displacement is now evaluated per hit in the ray tracer (`TurbWarp.h`): each texture axis is displaced by the sine of the other one, `texCoord + strength * (1/8) * sin(pi * texCoord.yx + time)`. In the units of the old auxiliary image the amplitude is 8 and the period 256, with the texture sampled at `image / 64`, i.e. an eighth of a texture tile of amplitude over a two-tile period — the `pi` factors cancel exactly — and the phase grows one radian per second, which matches both the old `cl.time * (128/pi)` and the `globalUniform.time` the water waves already use. Layer 0 goes through the warp in the primary, indirect and reflection/refraction hit paths (`HitInfo.inl`), together with the `dTdx`/`dTdy` derivatives that select the mip level, so the swirl stays sharp instead of smearing across LODs, and the any-hit alpha test (`RtAlphaTest.rahit`) samples the same warped coordinate — had the two disagreed about where a masked texel sits, geometry would punch holes in the surface. Only surfaces carrying the new per-instance `TURB_WARP` flag get it, which the engine sets on every `*`-named surface except water and slime: those two already move through the RT water's own wave normals, and running the classic warp on top would look like water coming to the boil. `rt_turb_warp` (default `1`) scales the amplitude and `0` freezes the surface again.
- **`color_emissive` materials key** — emissive masks no longer need a hand-painted `*_luma.png` per light: `color_emissive: ff0000` makes only the base texture's pixels close to that colour emissive, with the tolerance controlled by `color_emissive_threshold` (default `0.02`, i.e. a very strict ~2% colour-cube distance). The synthesized mask is **white** on an exact colour match and fades **exponentially to black** as a pixel's colour approaches the threshold, so a glow blends into the surrounding art instead of ending in a hard edge that looked like the texture was cut out with scissors and pasted on top. `emissive_factor` scales the result; combined with `is_light: true` the surface also casts light as a masked area light. Textures that have no shade of the exact colour therefore glow from a soft halo outward — widening `color_emissive_threshold` pulls more of the palette into the ramp. A `texture_emissive` key in the same entry takes priority over `color_emissive`: the colour key is ignored entirely while it is present (even if the luma file fails to load, which is reported at startup), while the classic fullbright mask is merged in addition. The brightness-based `synth_emissive` / `emissive_threshold` keys were removed (unused in `materials.yaml`).
- **Per-category ray counters and per-pass GPU timings** — `rt_stats 1` no longer shows only a frame total: every `rayStatsAdd` site is counted and the new `rgGetFrameStatsEx` / `RgFrameStats` reports the four categories separately (PRIMARY / REFL-REFR / INDIRECT / SHADOW, with `rgGetRaysPerCategory` for the whole list; the old two-out-parameter `rgGetFrameStats` entry point is kept). A second readout, `rt_pass_stats 1`, adds the GPU frame total and the cost of each of the fifteen GPU passes as a name and a millisecond value, measured with `VK_QUERY_TYPE_TIMESTAMP` queries written around every pass (`PassTimings`: one query-pool slot set per frame in flight, `vkCmdResetQueryPool` each frame, EMA-smoothed with a 0.9 factor so the numbers are readable instead of flickering) and named by `rgGetGpuPassName`. The pass block needs a queue that supports timestamps (`timestampValidBits != 0`, non-zero `timestampPeriod`); where it is missing, `gpuTimingValid` stays false and only the ray counters are drawn. Both readouts default to off.

### Removed
- **Extracted `progs/` base textures with swapped colour channels** — the twenty model and sprite images under `vkpt/Source/progs/` (`armor/`, `b_g_key/`, `b_s_key/`, `end1`–`end4`, `m_g_key/`, `m_s_key/`, `s_explod.spr/`, `v_shot/`, `w_g_key/`, `w_s_key/`) were extracted from the game paks and shipped as `texture_base:` overrides, but the extraction wrote them with **red and blue swapped**, so the models and sprites rendered tinted: the explosion sprite's warm frames came out blue (`s_explod.spr` frame 2 averages `(204,166,97)` in the pak and `(89,157,199)` in the extracted file, with identical coverage/alpha). The originals live inside the `.mdl`/`.spr` assets in the paks — which contain no `progs/*.png` at all — and the loader already falls back to the engine's own albedo when a material has no `texture_base` key or its file cannot be loaded (`gl_texmgr.c`: `RT_MAT_LoadTexture` → `albedoFallback`), so the twenty files and their twenty `texture_base:` keys were deleted together. `progs/` now holds only the 44 `_gloss`/`_luma` masks this project authors, and every remaining material reference resolves.
- **Material bump maps** — all 56 `*_n.png` material textures and their `texture_normals:` references are gone (45 under `textures/`, 11 under `progs/`). 17 of them (the wall, floor and window maps) were authored with the normal components in the wrong channels — `R = 0` for every texel, `G = n_y`, `B = n_x` — while the loader reads `n.x` from `R` (`gl_texmgr.c`), so `n.x` decoded as the constant `0 * 2 - 1 = -1` and every normal was tilted 45° into the surface. A mirrored surface bounces a ray about the shading normal, so the tilt doubled into a **90° rotation of the reflection** on vertical surfaces: `window02_1` on `start` reflected the room sideways instead of upright, while flat-shaded ammo boxes looked correct. The other 39 maps were a uniform identity `(128,128,255)` and changed nothing at all. With `rt_normalmap_stren 0` the affected surfaces already looked as intended, so the assets were dropped instead of re-authored — with no `texture_normals` the loader fills the normal texture with the identity value and shading falls back to geometric normals. The renderer's support for the key (`rt_normalmap_stren`, the identity fill, `bump_scale`) is left in place, so a corrected map can be re-added as data alone.
- **Stale renderer leftovers** — two leftover files from the vkpt rename (`GenerateShaderCommon.py`, `CmQ2LightListBuild.comp`) that nothing referenced were deleted; the vendored renderer now lives entirely in `vkpt/`.
- **Startup resolution dialog** — the "High-resolution" MessageBox that asked for a screen resolution before the game window opened was removed.

### Fixed
- **Projectiles and monsters disappeared in, and behind, water** — a map's vis data can grow a one-way barrier along a water surface (dry leaves see liquid leaves, but no liquid leaf sees any dry leaf). `SVFTE_BuildSnapshotForClient` drops an entity when none of its leaves is in the client's fat PVS, and that PVS is built from the *client's* leaves, so from dry land it contains **no liquid leaves at all** and every rocket, spike, grenade, monster or pickup standing in a pool was never put into the snapshot (measured on `e4m1`: 0 of 476 liquid leaves reachable). Classic water was opaque enough to hide the bug; the ray-traced refraction passes show straight through the surface, so the entities simply were not there. Maps whose vis data is sealed like this are now flagged at load (`Mod_CheckWaterVis` → `nowatervis`) and a PVS-culled entity is kept when a world line-of-sight trace from the eye to its bounding box is unobstructed — clip and sky block it, water does not. The trace runs only for entities the PVS rejected, so normal occlusion culling is untouched: on `e4m1`/`start` it adds 0–3 brush models (0–18 faces) per vantage, whereas blanket-sending everything the PVS hid would have added ~500 faces of doors, walls and triggers per frame (an entire level's brush geometry, i.e. the visible frame-rate drop of the first attempt).
- **Lava lit only what the camera could see** — emissive liquids (`*lava1`) were excluded from the whole-map emissive bake and instead re-uploaded every frame from the water texture chains, which only contain surfaces inside the current PVS and view frustum. Lava light therefore "followed" the view direction (pools glowed one-sidedly) and vanished entirely where the lava surface was culled. Lava is static world geometry, so it is now baked like every other fixture at map load and re-uploaded per frame from the baked list with live lightstyle scaling; only brush-entity liquids keep the per-frame dynamic path. Non-light liquids (water, slime, teleports) are unaffected.
- **Whole texture glows on lamp boxes flush to the ceiling** — `tlight08` had `is_light: true` but no `texture_emissive` luma mask, so the engine treated it as a *uniform* area light: every face using the texture glowed over its full area. On lamp boxes wrapped in the texture on all sides (ceiling/floor fixtures) the side faces shone horizontally into the room, over-lighting walls and making the lamp itself look dark. `tlight08` is now `is_light: false` (its light comes from the matching `tlight01`/`tlight07` bottom face); the texture was used on 331 faces across the maps, 244 of them side faces.
- **Button/lamp brightness re-tuned** — `+0basebtn`, `+abasebtn`, `basebutn3` and `window03` no longer synthesize their emissive mask from a colour key (`color_emissive` `d70000`, `dbcb13`, `ff0000`, `7f0000`) but read authored masks (`+0basebtn_luma.png`, `+abasebtn_luma.png`, `basebutn3_luma.png`, and the already-present `window03_luma.png`), so their glow follows the drawn glyph instead of a colour-cube distance; `+0basebtn`/`+abasebtn` drop from the default 1.0 to 0.3 (they were the brightest lights on the map), `basebutn3` stays at 0.1 and `window03` goes 0.2 → 0.5 (it had been a very dark red), while `tlight11` 0.5 → 0.7, `tlight09` 0.5 → 0.4 with the `tlight07_luma.png` glyph mask in `ffec15`, and `tlight05` keeps its brightness but changes its light colour to the cold `b0b0ff` over `tlight05_luma.png`.
- **Lightning bolt glows** — `progs/bolt.mdl:frame0` and `progs/bolt1.mdl:frame0` (the lightning gun bolt models) are now emissive lights with pale-blue `ccccff` light, replacing the old `force_rasterize`/`is_light: false` entry that left the bolt invisible to the ray tracer. The `texture_emissive` mask they point at (`mdl_skins/bolt_skin0.png`) had never been committed, so the bolts lit uniformly and the loader reported the missing file at startup; the mask is now in the repository as a decode of the bolt's own skin, so the glow follows the model's shape (pale blue, `(127…215, 191…255, 255)`, close to uniform on the shaft and dimmer at the rim).
- **Most of a cluster's lights were never sampled** — the ported Q2RTX light-selection CDF (`q2SampleClusterLights`) picked the partition of the cluster's 64-slot light list with `floor(rng.x * partitions)`, computed the within-partition residual `r0 = rng.x*partitions - partition` — and then ran the inverse CDF with the *full* `rng.x` instead of `r0`. That correlates the block index with the entry index and confines the distribution to the `[f/partitions, (f+1)/partitions)` slice of the block's mass: with an 8-entry block only ~1/8 of the entries can ever be selected, and which ones they are depends purely on the light's position in the list. Lights that fall off that diagonal get **zero** contribution inside those clusters, so a lamp can light one leaf and be a hard-edged, "invisible wall"-bounded dark region in the next one, physically identical lamps behave differently, and walking across cluster boundaries changes which lights are reachable (uneven static light, mottled muzzle flashes, shadows "popping in"). Upstream (`references/q2rtx/.../light_lists.h`: `rng.x -= fpart;` then `rng.x *= mass`) uses the residual; the CDF now does too.
- **Lights vanished in rooms split across several clusters** — a cluster's light list is built from the PVS of the cluster's origin, so a surface in a corridor or a dense room whose cluster's PVS does not reach a lamp got an incomplete list (or a different one than the neighbouring cluster) and, with the sampling fix above applied to a short list, went abruptly dark: a room thick with `*_luma`/TAL emitters kept only a fraction of them, and rockets/explosions stopped lighting walls a few metres away. After the PVS pass, every cluster is now topped up with the **8 nearest lights within `rt_light_reach`** that the PVS did not grant (`RT_CLUSTER_TOPUP_LIGHTS`), selected by distance to the cluster's own light origin, so nearby dynamic lights are present in every cluster they can reach. Top-up lights take a slot on demand and are released in a later frame exactly like the PVS-assigned ones, so no light is permanently excluded.
- **Dynamic objects are lit again** — doors, lifts, buttons, monster/weapon/pickup models no longer render unlit. Brush-entity (submodel) surfaces were assigned the cluster of the SOLID leaf inside the brush (empty light list); they now resolve the visible leaf by sampling their face centroid offset along the surface normal (Q2RTX approach). Alias models (monsters, ammo, keys) get the BSP cluster of their origin leaf instead of the default cluster 0, so they're lit by the same cluster light list as the surface they stand on.
- **Dim emissive surfaces cast light again** — health kits, ammo boxes and similar small indicators were baked as emissive area lights only if the length of their average emitted colour cleared `0.01`; those masks are a few dim pixels over a large texture (measured 0.001–0.009), so they were silently dropped as "no light color" and lit nothing. The rejection threshold is now `0.0005` (~0.13/255, i.e. quantization noise), which admits all of them while still skipping fully black masks.
- **Fixtures no longer light up where they are not yet standing** — the whole-map emissive bake swept every surface of the world model, including inline brush models (doors, plats and lamps that slide out of their niche on a trigger). A baked light then already sat at the fixture's **final** position, so the room lit up before the lamp arrived. Inline-brush surfaces are excluded from the static bake and are lit dynamically instead, so a moving lamp takes its light with it.
- **Base RT brightness lowered ~25%** — a uniform exposure reduction (`tmExposureBias` −2.8 in the tonemapping pass, ~1.9 stops under the stock default) darkens the whole image, and the auto-exposure is muted in dark scenes so the dimmer look isn't compensated back up: the adaptation target floor (`tmMinLuminance`) is raised from 0.0002 to 0.02, and the dark→bright adaptation speed (`tmExposureSpeedUp`) is halved so the image brightens more slowly after leaving a dark area. Bright scenes are unaffected — their target luminance sits above the floor.
- **Classic fullbright surfaces emit light again** — buttons, switches, light panels and runes whose brightness came from the classic Quake fullbright mask were rendered with `emiss = 0` because the Q2RTX-style `.mat` synthesis overwrote the emissive material. The fullbright mask is now merged into the material's emissive channel (keeping the `.mat` normals/gloss), so these surfaces glow and respond to `rt_emis_maxscrcolor` / `rt_emis_fullbright_dflt` (the latter's default was raised 32 → 255).
- **Ghosting around bright emissive surfaces** — while the camera moved, bright emissives (buttons, lava) left trails because the temporal accumulator's LF/HF channels had no motion term (only the specular channel did) and kept the bright history for ~170 frames. A motion-driven antilag term is now applied to the LF/HF channels too, so the history converges in a few frames during movement while static frames are unchanged.
- **Red lamps and dynamic lights wash over their surroundings again** — the direct pass applied Q2RTX's *indirect-bounce* firefly clamp (`max_solid_angle 0.02`, `bounce >= 1`) to first-hit sphere/spot lights as well, attenuating close lights by up to ~26× and washing out their chroma (a red lamp lit the wall pale pink instead of vivid red). The direct pass now caps at `2π` exactly like Q2RTX's `bounce == 0` path, and sphere lights (lamps, lava balls) are no longer forced one-sided by the triangle-light spotlight factor — so they color walls around them, not just in front of their emission normal.
- **Emissive luma masks are stencils again, not solid colour plates** — `rt_emis_maxscrcolor` had defaulted to 320 since the v3.6.0 "emissive chroma boost" commit (`3489e87`). The on-screen emissive add is `albedo * luma coverage * value` in `CmPrepareFinal.comp`, so at 320 every non-zero mask texel exceeded 1.0 and clipped to the same flat saturated colour: the EXIT sign rendered as a solid red rectangle, lamps grew a pale rim and the activated green button looked like a full-texture overlay. The default is now 4, so only the masked glyphs glow and the surface keeps its authored colour. (Upstream shipped 125, which clips just as well — the value only has to stay small.)
- **Filtered pale rim around masked emissives** — `rt_emis_sharpmask` (default 1) snaps the luma-mask read to texel centers while the texture is magnified (`HitInfo.inl`), so binary masks keep hard edges instead of a filtered halo between lit and unlit texels.
- **Missing luma masks restored** — `materials.yaml` pointed at nineteen emissive textures that were never committed: six lamp masks (`textures/{tlight01,tlight02,tlight07,tlight10,tlight11,rune2_3}_luma.png`) and the thirteen button, key, rune, light-fixture and window masks added with the emissive work (`textures/{+0shoot,key03_1,light1_4,light3_5,light3_6,light3_7,light3_8,metal6_3,quake_butn,rune2_2,rune2_4,rune2_5,window03}_luma.png`). Those surfaces lost their emissive/TAL light on a clean checkout while an old build directory kept stale copies alive. All nineteen are now in `vkpt/Source/textures/`, so every emissive reference in `materials.yaml` resolves — the last missing mask, `mdl_skins/bolt_skin0.png`, arrives with this change (see the bolt entry above) — and `textures/tlight02` also pointed at `tlight10_luma.png` (the two files are byte-identical) and now points at its own mask. `z_exit_luma.png` was likewise generated as an albedo-brightness threshold, leaving a level-64 plate across the whole panel — it is now strictly binary and covers only the letter glyphs.
- **Geometry under water was clipped away by the depth test** — `RsDepthCopying.frag` copies the depth of the frame that the reflection/refraction pass renders into, and that pass left only the *water surface* in it: anything rasterized below the water line then failed the depth test and was cut away, so looking through a pool removed the floor and the geometry behind it (the ray-traced image was correct; the raster composition was not). The refraction hit now writes its own NDC depth — `projection * view * vec4(hitPosition, 1)`, `clamp(z / w + 1e-5, 0, 1)` — for **both** checkerboard pixels of the refraction pair, and a refraction ray that leaves into the sky writes `1.0` so a sky pixel cannot clip the geometry behind it. `FB_IMAGE_INDEX_DEPTH_NDC` was also missing from the barrier list of `TraceQ2ReflectionRefractionRays` even though that pass is what writes it, and without the barrier the write could be lost — which is why an earlier attempt at this fix appeared to change nothing.
- **Rasterized transparent surfaces were never composited** — the primary pass stores the raster pass's transparent layer (premultiplied decals and `force_rasterize` sprite models: spikes, grenades, the laser and the bolts) into `framebufQ2Transparent`, but nothing outside the producing pass ever read that buffer, so the layer never reached the image and those surfaces could not appear over a ray-traced surface. `CmQ2Atrous.comp` (the a-trous pass that also composites the denoised result) now blends it in immediately before the volumetric fog — `transparent.rgb + illuminated * (1 - transparent.a)`, then the fog on top, Q2RTX's order — so transparency is composited in the same pass as the shading it sits on instead of being discarded.
- **Contour banding in dark areas, "as if every shader were 8-bit"** — the composite is written to `framebufFinal` as linear `r11f_g11f_b10f` (6/6/5 bits of mantissa, so ~1.6% relative precision on R/G and ~3% on B) and the present blit converts it to 8-bit sRGB, and **nothing dithered either step**: smooth gradients in shadow therefore resolved into flat contour bands, each one a pair of adjacent 8-bit codes, with the effect growing as the area gets darker and spans fewer codes. `CmPrepareFinal.comp` now adds a triangular-PDF dither of one output code immediately before its `imageStore`. The amplitude is derived as `(1/255) / (d(encode)/d(linear))` — `12.92` below the sRGB knee and `(1.055/2.4)·l^(1/2.4−1)` above it — because the buffer holds **linear** light and the sRGB encode happens later, in `BlitForPresent`; a flat `1/255` would have been wrong by up to ~8× in the shadows where the bands are. The spatial structure is interleaved gradient noise (Jimenez) plus a per-channel white hash, i.e. the sum of two uniform samples, so the pattern reads as grain instead of speckle; the blue-noise dither Q2RTX uses could not be reused, because it lives in the raster `screen_effects.comp` that the RT-only present path never runs, and this pass does not bind the blue-noise texture. The dither is deliberately static rather than per-frame — it adds no temporal noise and is not averaged away by the upscalers, which read the finished FINAL buffer — and it also covers the `r11f_g11f_b10f` step itself, one sRGB code being roughly 2–3 ULP of that format. `OUTPUT_DITHER_CODES` (default `1.0`, in `CmPrepareFinal.comp`) scales the amplitude.

### Changed
- **Teleport surfaces are ordinary surfaces again** — the RT portal effect (a mirrored copy of the destination built out of reflection/refraction rays) has been wrong from behind since it went in: approaching a teleport from the "back" showed the mirrored destination instead of its texture, and every portal pixel paid for its own portal pass. `rt_teleport_portals` now defaults to `0`; with it off the surfaces upload as plain opaque geometry — `RT_UploadAllTeleports` returns immediately, and the portal branch of `RT_FlushBatch` (`RG_GEOMETRY_PASS_THROUGH_TYPE_PORTAL`, the reflection albedo-add flag and the per-portal geometry upload) is skipped, so no reflection ray is spent on a teleport at all and the effect costs nothing while it is off. The debugging aids went with it: the `rt_pfnportal` command, `RT_PrintNearestPortal` and the `world_custom_portals.txt` destination patch table (`LoadCustomTeleportInfoAndPatch`) were removed. Teleports will be reimplemented through a Q2RTX "camera" material; `rt_teleport_portals 1` restores the old behaviour in the meantime.
- **The engine is QuakeRay now (0.9.0)** — the fork stops being named after the code it came from: `ENGINE_VERSION` goes `0.30` → `0.9` and the `alpha` suffix is dropped, so the version string is `0.9.0` and every place that used to print `vkQuake`/`vkQuakeRay` prints `QuakeRay` (window caption, console banner, main menu, startup log, the `version` command and the SDL application name). The CMake project and executable target are `quakeray`, so the build now produces `build\Debug\quakeray.exe` instead of `vkquake.exe`; `build_win.ps1` and the `build\<Config>\id1` game-data layout are unchanged. `Windows/vkQuake.rc` → `Windows/QuakeRay.rc` (with `vkQuake.ico` → `QuakeRay.ico`), `Misc/vkQuake_{256,512}.png` → `Misc/QuakeRay_{256,512}.png`, and the CI workflow, VS Code launch configurations, AppImage packaging scripts, `.gitignore` and `vkpt/` CMake comments follow the rename. The Linux/macOS user directory moves from `.vkquake` (`~/Library/Application Support/vkQuake`) to `.quakeray` (`~/Library/Application Support/QuakeRay`). Two names deliberately keep the old spelling: the shipped game data pak stays `vkquake.pak` (it is content the engine auto-mounts from the game directory, not the engine binary), and the engine name passed to CSQC *(`CSQC_Init`'s first parameter)* stays `vkQuake`, which is the name mods use to recognise this host.
- **Second diffuse bounce disabled by default** — `rt_indir2bounces` now defaults to `0`. The indirect pass can take a second *diffuse* bounce off the first bounce hit and gather `(emission + directLight) * albedo` there (`rt_indir2bounces 1`, which matches Q2RTX's `indirSecondBounce`), but an A/B on `start` produced a frame indistinguishable from single-bounce rendering while the ray count rose ~30% — 16.5M → 21.5M at 1080p, i.e. one extra indirect ray plus up to two shadow rays per pixel. The second bounce therefore stays off until its contribution is understood; the code path and the cvar are unchanged.
- **Emissive light colors surfaces more vividly** — the emissive (glow) contribution of bounce hits is chroma-boosted (`EMISSION_CHROMA_BOOST 8.0`), so lava tints nearby walls a vivid orange-red instead of pale pink; the reflected direct-light contribution gets a milder chroma boost (`LIGHT_CHROMA_BOOST 1.3`).
- **Default sky and sun settings** — new defaults: `rt_physical_sky 1`, `rt_sun 1` with the sun at `rt_sun_pitch 140` / `rt_sun_yaw 120` (it used to sit at 60/−40, i.e. low and off to one side of `start`), `rt_sky 1` (it used to be 9, a nine-times-brighter sky, which is what made the sky's ambient light tint everything), `rt_sky_brightness 1`, sky display color `32/0/64` (`rt_sky_color_r/g/b`), sky light color `32/0/64` (`rt_sky_light_r/g/b`), `rt_sky_clouds 1` with cloud color `0/0/0` (`rt_sky_cloud_color_r/g/b` — the procedural clouds are composited straight over the sky colour, so they now read as dark cloud over the coloured sky instead of white), `rt_sky_cloud_speed 0.3`, `rt_sky_cloud_coverage 0.2`, `rt_sky_cloud_density 0.8`, plus the new `rt_sky_ambient_lod 4`, `rt_sky_nee 1`, `rt_indir2bounces 0` and `rt_pass_stats 0`.
- **Sky light is no longer a flat wash over everything** — the ambient sky term that the indirect pass adds when a bounce ray misses geometry sampled the sky cubemap at a LOD derived from the surface roughness without any cap (up to `10`, i.e. a 2×2-texel average of the whole sky), so rough walls, floors and ceilings all received the *same* direction-independent sky colour and the sky↔horizon gradient, the sun-side bias and the cloud structure never reached the shading. Both GI sky-hit sites in `RtQ2Indirect.rgen` now clamp that LOD with the new `rt_sky_ambient_lod` cvar (default `4` — a 64×64-per-face mip that keeps the gradient while staying low-frequency; `0` gives the most directional sky light, `10` restores the old flat wash). The visible sky and the specular reflection/refraction path are untouched, and the change costs **no extra rays**.
- **Sky light is sampled as a light (NEE)** — the sky contributed to indirect diffuse only through the *escape* event of the specular bounce: the sample radiance was the sky cubemap read at the bounce direction, carried by the whole combined BSDF, so on rough surfaces the sky arrived as a direction-blurred wash that tinted whatever it landed on rather than a light with an occluded hemisphere. Every indirect diffuse sample now additionally takes an explicit sky sample with the cosine-hemisphere distribution the bounce already uses, traces one visibility ray to it and weights it against that bounce with multiple importance sampling — a new analytic GGX-VNDF partner pdf (`evalSpecularBouncePdf`: `G1(n·v) · D(n·m) / (4 n·v)`, zero for a degenerate lobe), with the bounce-hit sky term keeping the complementary weight, so the two estimators split the same energy instead of counting it twice and the sky is no longer at the mercy of whichever lobe happened to be sampled. The lookup is the same `rt_sky_ambient_lod`-capped one described above (`roughness * (SKY_MIP_COUNT - 1)`), so the gradient, cloud and zenith structure survives. Cost: one extra shadow ray per indirect diffuse sample; `rt_sky_nee 0` restores the old result exactly (the MIS weights collapse back to 1 and 0).
- **Shadow rays are no longer traced where they cannot be seen** — three changes at the shadow-ray sites, none of which is visible in the image: a shadow ray is only traced when the shading normal faces the emitter (`dot(n, L) > 0`), the NEE light and sun samples of the *second* diffuse bounce are skipped under the same test (`processSecondDiffuseBounce`), and shadow rays terminate at the first hit (`gl_RayFlagsTerminateOnFirstHitEXT`, the payload is a boolean) instead of walking all the way to the light. The `SHADOW` counter now counts rays that were actually traced, so `rt_stats` stops reporting the rays that were skipped. On `start` at 4K, standing at the water, the frame dropped from 65,389,784 to 58,361,279 rays (−7.03M, −10.7%) and became roughly 2 FPS faster with no visible difference in the A/B — with no bump maps left in the materials, a shading normal can only face the light when the geometric one does.
- **Dropped all remaining legacy-renderer references** — CI now builds only the vendored vkpt renderer (no external clone, no dead `vkpt_SDK_PATH` flag); comments in the root and `vkpt/` CMakeLists no longer mention the old renderer dll; the renderer dev-config default file was renamed to `vkpt.txt`.
- **Buttons, floor switches, the teleport top and the EXIT box are lights now** — the four numbered variants of the button and floor-switch textures (`+0button`–`+3button`, `+0floorsw`–`+3floorsw`, one shared mask per family: `+0button_luma.png` and `+0floorsw_luma.png`) and `tele_top` were plain textures with no emitter at all; they are now masked area lights in warm `f5902a` (teleport top `ffe613`, mask `tele_top_luma.png`), with four brightness steps per family (buttons 0.3 / 0.6 / 0.9 / 0.12, floor switches 0.03 / 0.06 / 0.09 / 0.12) and the matching `+abutton` / `+afloorsw` / `+ashoot` entries left non-lighting for the frames that should not cast, so a lit button and a dead one no longer read the same. The EXIT box sides and top (`+0_box_side` / `+1_box_side` / `+0_box_top` / `+1_box_top`, masks `ex_box_big_luma.png` / `ex_box_small_luma.png`, 0.1 and 0.3), the ceiling panel `ceil1_1` (0.3, `is_light: true`) and `comp1_6` (0.05 → 0.3) fill in the rest of the fixture set, which is what gives the machine rooms their local glow instead of a flat ambient term.
- **Lamp and panel brightnesses re-tuned once more** — the half-brightness `+0_med25` / `+0_med25s` go 0.5 → 0.2 and the whole `med100` family (plus `+1_med25`, `+1_med25s`, `+2_med25`) 0.5 → 0.3, `z_exit` 0.1 → 0.2 with `metalness_factor 0.1`, and the four `twall*` wall panels stop being area lights: they are emissive-only at 0.15–0.25 (`twall1_1` 0.05 → 0.15 and rasterized, `twall2_1` 0.05 → 0.25 with its `light_color 7b7baf` dropped and its rasterization turned off, `twall5_1` 0.05 → 0.2, `twall2_2` 0.1 → 0.2), so a wall that carries a thin glowing strip no longer lights the room with its entire surface.
- **`progs/laser.mdl` is a light, and more sprites are rasterized** — `progs/laser.mdl:frame0` goes from `is_light: false` to an emissive light (`EFD1A7`, 0.8) so the laser's own glow lights its surroundings instead of only being traced, `progs/w_spike.mdl:frame0` goes from a barely-there 0.01 to 0.5 in green-yellow `CBEF80` with `metalness_factor 0.1` (the held spike used to render as a dark silhouette at close range), and `progs/grenade.mdl:frame0`, `progs/spike.mdl:frame0` and `progs/s_spike.mdl:frame0` become `force_rasterize: true` so those sprites are drawn by the raster pass instead of being traced.
- **`textures/+0planet` points at a mask that exists** — the entry referenced `textures/+0planet.png`, a file that is not in the repository (the loader reported it at startup), so the panel had no mask to follow; it now reads the authored `textures/+0planet_luma.png` at 0.1 over `b2b2ff`, and it is no longer an area light (`is_light: false`), so the panel glows without lighting the room around it.

## v3.4.0

### Added
- **Q2RTX per-BSP-cluster light lists** — the camera-centered 16³ cell grid was replaced with the real Q2RTX mechanism: the world model's BSP leaves are used as clusters and the PVS is used for cluster visibility. Each light is added to every PVS-visible cluster from its own leaf (no distance-based cutoffs), and occluded lights are excluded per cluster. The direct/indirect passes look up the light list by the BSP cluster of the hit (per-pixel cluster texture for primary hits, per-triangle cluster for bounces). The GPU light-list build (`CmQ2LightListBuild.comp`, `LightGrid`) is gone.
- **Square light patches fixed** — torch / muzzle flash / explosion lights no longer cut off at cell-grid boundaries (the light lists had a distance cutoff that bright lights exceeded, producing quadrilateral patches on walls). The classic lightmap is no longer applied as a shading layer on top of the ray-traced albedo either.
- **Classic lighting fully disabled in the RT renderer** — `R_PushDlights`, `R_RenderDynamicLightmaps` and the lightmap SHADE layer in the RT world material are all skipped unless `rt_classic_render 1`. The ray tracer produces all the lighting (Q2RTX model).
- **Cluster data in the world geometry** — every world vertex carries the BSP leaf ("cluster") of its surface (`rt_surfcluster[]` in the game; `RgVertex.cluster` in the renderer).

### Changed
- **Renderer renamed to vkpt** — the vendored renderer folder, public headers (`vkpt.h`/`vkptA.h`), the C++ namespace and the CMake target are now named `vkpt` (Q2RTX-style name). No functional changes.

## v3.3.0

### Added
- **Decoupled from RayTracedGL1.dll (4.7)** — the Q2RTX-style ray-traced renderer is now vendored into the repository (`vkpt/` folder: source + shaders + KTX/FidelityFX) and built as a static library linked into `vkquake.exe`.
- **The game no longer depends on the RayTracedGL1 library** — `RayTracedGL1.dll` is not required at runtime anymore; the renderer is compiled straight into `vkquake.exe`. The public `RG_*` API is kept as an internal interface (`RG_STATIC`); the `.spv` shaders and blue noise are still loaded from the game data (`ovrd/shaders/`, `ovrd/BlueNoise_LDR_RGBA_128.ktx2`). The renderer's own changelog is preserved at the bottom of this file.

### Changed
- **The legacy (pre-Q2RTX) renderer was removed** — the Q2RTX-style core is now the only renderer (`rt_core_q2rtx` cvar removed; `coreQ2RTX` is always on). The legacy SVGF denoiser path, legacy screen-space volumetric (`rt_volume_type` no longer renders) and the legacy reflection/refraction pass are gone. Kept: the ASVGF denoiser, the TAAU upscaler (default), **FSR 2/FSR 3.1/DLSS upscalers still available** (they run on the Q2RTX final image when selected in the video menu), god rays, fog volumes, procedural sky, ReSTIR lighting, and the classic (non-RT) renderer fallback.
- Fixed an intermittent AMD overlay flicker (gone together with the legacy render path).

# vkpt renderer (vendored) — changelog

The RayTracedGL1 renderer is now part of this repository: it is built from source (`vkpt/`) and linked into `vkquake.exe`, so **the game no longer depends on the external `RayTracedGL1.dll` library**. Its changelog is preserved below.

## v3.0.0 (vkpt renderer)

### Added
- **Q2RTX-style core rendering path** — a full new pipeline alongside the legacy one, switched at runtime by the host flag `RG_DEBUG_DRAW_Q2RTX_CORE_BIT` (`rt_core_q2rtx` cvar in vkquake-ray):
  - **ASVGF denoiser** ported from Q2RTX (`asvgf_*.comp`): temporal accumulation, low-frequency (YCoCg luma-SH) and high-frequency/specular atrous filtering, checkerboard interleave
  - **Checkerboard interleave + TAAU** (Q2RTX `taa`) replaces FSR/DLSS upscaling on the new path; FSR 2/3 and DLSS remain available on the legacy path
  - ReSTIR (direct/indirect) remains the lighting solution — `CmQ2Adapter` converts its output into the ASVGF color format (LF_SH / LF_COCG / HF / SPEC)
  - 29 new Q2-format framebuffers (ASVGF colors, history/moments/RNG, TAA history)
- **Fog volumes** — port of Q2RTX `fog.c` + `find_fog_volumes` / `evaluate_fog`:
  - New public API: `rgSetFogVolumes`, `RgFogVolume` (AABB via two diagonal points, color, half-extinction distance, optional soft face), `RG_MAX_FOG_VOLUMES` = 8
  - `CmQ2Fog.comp` blends up to two closest fog volumes along the camera ray in HDR, before tonemapping; works on both the legacy and the new Q2RTX path
- **Q2RTX noise-aware tone mapping** (histogram + curve + apply, Eilertsen et al. + NVIDIA mods)
- **Sun shadow map + god rays** — depth-only world render from the sun's view, ray-marched volumetric light at half-res with a bilateral filter
- **Procedural physical sky** — `RG_SKY_TYPE_PROCEDURAL`: analytic single-scattering atmosphere (Rayleigh + Mie), sun disc, procedural fBm clouds (no textures), HDR cubemap 1024², cached when clouds are off

### Fixed
- **std140 layout of scalar arrays in generated C headers** — GLSL std140 aligns every array element to 16 bytes, but the header generator emitted scalar arrays with a 4-byte stride (e.g. `uint[8]` became `uint32_t[8]` = 32 bytes instead of 128), shifting every field after the first scalar array by 96 bytes on the CPU side. The GPU then read garbage (fog volumes silently never rendered while host-side diagnostics looked correct). The generator now emits `count*4` scalars per std140 array element

## v2.2.0 (vkpt renderer)

### Fixed
- **Denoised ghosting** — `CmSVGFTemporalAccumulation.comp` reworked to remove ghosting artifacts in the SVGF/ASVGF temporal accumulation

## v2.1.0 (vkpt renderer)

### Added
- **AMD FSR 3.1 upscaler** via FidelityFX SDK 1.1.4 (`ffxCreateContext` / `ffxDispatch` / `ffxQuery` API)
- `RG_RENDER_UPSCALE_TECHNIQUE_AMD_FSR3` — new public enum value for FSR 3.1
- `RG_RENDER_RESOLUTION_MODE_NATIVE_AA` — Native AA mode (render at 1.0x, FSR 3.1 anti-aliasing only)
- AMD-signed prebuilt `amd_fidelityfx_vk.dll` required at runtime (driver overlay detection depends on Authenticode signature)
- **Explicit FSR version selection** — vkpt tells the FidelityFX framework which FSR algorithm to use via `ffxOverrideVersion` instead of letting the framework pick the "best" provider by itself:
  - `RG_RENDER_UPSCALE_TECHNIQUE_AMD_FSR2` → FSR 2.x
  - `RG_RENDER_UPSCALE_TECHNIQUE_AMD_FSR3` → FSR 3.1
- Switching between FSR 2 and FSR 3.1 works at runtime (the FidelityFX context is recreated on version change)
- If the requested FSR version is not present in `amd_fidelityfx_vk.dll`, vkpt falls back to the other version and prints a message to the game console (`pfnPrint`)
- `rgIsRenderUpscaleTechniqueAvailable` now actually checks whether the requested FSR version exists in the DLL

### Changed
- FSR 3.1 is always enabled (no compile-time flag; `RG_USE_FSR3` is unconditional)
- `Source/FSR3.{h,cpp}` renamed to `Source/FSR.{h,cpp}`, class `FSR3` renamed to `FSR` (it now handles both FSR 2 and FSR 3.1)

### Removed
- Old FSR2 code (`Source/FSR2.cpp`, `Source/FSR2.h`)
- `RG_WITH_FSR3` CMake option — FSR 3.1 is always built-in

### Fixed
- **AMD RDNA 4 (RX 9070 XT) crash at startup with `VK_ERROR_OUT_OF_DEVICE_MEMORY`** — VMA custom pools (`texturesStagingPool` / `texturesFinalPool`) used a fixed `memoryTypeIndex` that pointed to the wrong memory heap on RDNA 4. Fix: on AMD GPUs, pools are no longer created; `VMA_MEMORY_USAGE_CPU_ONLY` and `VMA_MEMORY_USAGE_GPU_ONLY` are used directly, letting VMA pick the correct heap. Non-AMD GPUs are unaffected
- Missing `VK_KHR_get_memory_requirements2` device extension (caused crash in `ffxCreateContext`)
- DLL digital signature required by AMD driver overlay for FSR detection
